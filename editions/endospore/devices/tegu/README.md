# tegu — Google Pixel 9a

`tegu` is the device-tree **codename** for the Pixel 9a (Google's name; used by GrapheneOS + the build:
`lunch tegu-cur-user`, `vendor/google_devices/tegu`, `os-tegu`, `generate-release.sh tegu`). This dir is
the **device tier** (see AGENTS.md "Repository layout") under the Endospore (GrapheneOS) edition — only the
bits hardcoded to *this* device:

- `vendor/etc/os-ref` — `os-tegu`, the per-device OTA payload ref.
- `vendor/etc/default-home` — the page-2 home seed (`nowhere_roamd.sh seed_home()` injects it into a fresh
  roamed profile's `launcher.db`; GrapheneOS Launcher3 only imports the dock from the overlay).
- `vendor/overlay/.../Launcher3/res/xml/default_workspace_5x5.xml` — the home layout for the 5×5 grid
  (empty landing + 5-app dock).
- `vendor/overlay/.../Settings/...` — the boot-brand image, the `fallback_home_finishing_boot` layout, and
  the themes overlay (branded boot hold).
- `patches/launcher3-grid.sh` — forces the 5×5 grid + icon size (source patch of the shared Launcher3
  `device_profiles.xml`; can't be an RRO — see the script header).
- `patches/launcher3-media-progress-ring.sh` — ports the #129 offline-media prefetch ring into Launcher3.
- `patches/launcher3-media-ring-smooth.sh` — smooths the #129 ring animation (#128 / #172 issue 4).
- `patches/launcher3-qsb-firstscreen.sh` — flips `QSB_ON_FIRST_SCREEN=true` so the empty leading page survives.

## Provenance / parity with lynx
tegu **mirrors lynx** (Pixel 7a): every file here except `os-ref` is byte-identical to `devices/lynx`. The
launcher `patches/` patch the **shared** GrapheneOS Launcher3 source (device-agnostic), and are carried here
so the tegu device dir is self-contained per docs/device-onboarding.md
(checklist item 6). The 9a and 7a fall in the same Launcher3 5×5 "Large Phone" grid bucket, so the grid patch
applies identically; the annotated rationale lives in `devices/lynx/patches`. **Verify the 5×5 grid on-device
when a physical 9a is flashed** — if Launcher3's default-candidate selection differs on the 9a's exact
display metrics, adjust `launcher3-grid.sh` then.

## Assurance tier
**Full** — relocks against our custom AVB key → verified boot (yellow) + rollback protection, plus the Titan
security element, same as lynx/stallion. The signed factory zip + web installer are **built, signed, and
staged** on the pilot (nowhere-cloud #81 — one-click WebUSB unlock → flash → boot-verify → relock). The
full on-device validation loop (gate → blind login → roaming restore → power-off wipe → re-login → OTA
self-update → relock + re-validate — checklist item 8) is **satisfied on hardware as of 2026-09-13**: a
tester runs a physical Pixel 9a, **relocked against our custom AVB key**, which boots and works as expected
(`NWP-20260913-16`). ⚠ Recorded as a FIELD REPORT, not a walked validation table — nobody stepped the
seven stages against the reference sheet and recorded each one. The build/sign/relock recipe is
byte-identical to the stallion path proven end-to-end on 2026-07-19.

Keys are **off-repo** (checklist item 5): `tegu` release/platform/AVB/OTA keys are generated by
`editions/endospore/build/gen-keys.sh tegu` ~~into the build tree's `keys/tegu/`~~ *(superseded 2026-11-05,
`NWP-20261105-19`: into the keys home's `tegu/` (`$NOWHERE_KEYS_HOME`) on a host that has one; a tree reaches them
through its `keys/` link, `docs/release-runbook.md` §1b)*, never committed.

A second Pixel adds a sibling `devices/<codename>/`; nothing here belongs at the edition (OS) level.
