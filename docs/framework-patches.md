# Framework patches

These are edits to build trees we do **not** own — AOSP/LineageOS for Diaspore, GrapheneOS for Endospore, plus the kernel tree and the platform sepolicy tree. They are **not committed source**. What this repo holds is a set of reproducible `patches/*.sh` scripts; what ships is whatever those scripts managed to do to someone else's tree on the build host, before `m`. A `repo sync` of that tree reverts every one of them.

They exist because the roaming model breaks assumptions the platform treats as invariants. Android assumes a user is permanent, so it mints a fresh SSAID userkey, a fresh Keystore namespace and virgin per-app hardening state for every login; it assumes an account database is only ever written by the framework that has it open; it assumes an app that asks to draw over the lock screen has a right to; it assumes a device that dozed yesterday should doze again on boot. On an amnesiac phone those are not conveniences, they are defects — and in most cases the platform exposes no configuration, no shell verb and no overlay that reaches them. `## Why a framework patch at all` records, case by case, the non-framework attempts that were built, measured and killed. Read it before proposing an app-side alternative to anything below.

They are also the single easiest thing to ship a build without. Every one is silent when absent: no build break, no missing symbol, usually no log line. Two named incidents make the point — `#210` and `#112` were absent from **every** Endospore image the canonical build script ever produced until 2026-08-22, and `keystore-roam.sh` had only ever been applied by hand until 2026-08-30, both while every producer above them logged success.

**THE ONE RULE: a new framework patch is not done until it has a row in `## The register` and a section in this file.** Not when the script applies cleanly, not when the build is green, not when it is proven on hardware. A patch that exists only as a script in a `patches/` directory is a patch the next build silently drops. This is the same rule `AGENTS.md` states for durable facts — a fact recorded only in a script header does not travel to the person doing the next flash.

## How to use this file

**Before a build**, read `## The register` top to bottom. It is the pre-build checklist: it says who applies each patch (or that nobody does), what artifact it lands in, which partition must be reflashed for it to take effect, and how to prove the built image actually carries it. A `system`-only flash leaves `SystemUI` (`/system_ext`), the sepolicy grants (`/system_ext`), the default apps (`/product`) and the recovery titles (`vendor_boot`) stale — and stale reads exactly like never-applied.

**Each entry below the register carries the same fields, in this order:** upstream file(s) and the symbol edited · why it exists (the concrete problem, and the user-visible symptom where one was recorded) · why it has to be a framework patch (the non-framework attempts that failed) · what it changes mechanically · the build artifact and therefore the partition to flash · idempotency and what a re-run does · what happens if it is not applied · how to verify a built image carries it · the work ID and issue number · warnings.

**`unknown` is a real value in this file.** Several partitions are genuinely undetermined — nothing in this repo records where the launcher APKs install — and a `*` in the register marks a partition derived from a file path rather than stated by a script, a doc, or a flash that was actually performed. Confirm those on the build host before planning a partial flash. Do not replace either with a guess.

**Maintenance rule going forward.** A slice that adds, changes, deletes or re-anchors a framework patch reconciles this file in the same slice — the register row and the entry, not one or the other. A patch that moves between "applied by `build-device.sh`" and "applied by hand" changes its Scope cell, and that change is the point of the cell. A patch whose verification signal changes changes its Verify cell. Status that has gone stale here is worse than absent, because this file is read by someone about to flash.

**Where this file and a script disagree, the SCRIPT is authoritative for what it does** — it is the thing that runs. But do not quietly rewrite the entry to match and move on: **record the contradiction in the entry**, naming both sides and which one runs. Several already exist and are load-bearing. `AGENTS.md` described `keystore-roam.sh` as an opt-in carry driven by a keep-list that `NWP-20260830-03` deleted (resolved: `AGENTS.md` now states the unconditional carry, and `NWP-20261011-55` marked the script's own header; see the keystore-roam.sh entry); `AGENTS.md` titles `systemui-no-restart-doze.sh` as the boot-AOD-clock fix while `worklog.md` and `docs/backlog.md` state flatly that it does not fix the clock and that the claim it did was wrong; `endospore-brand-strings.sh` sits next to a README that still leads with the misdiagnosis PR #399 corrected; `settings-fallbackhome-resume.sh` has a header summary that is stale against its own injected code. Each of those is a fact someone paid for. Resolving one silently deletes the evidence and invites the next person to re-derive it.

The same applies to `AGENTS.md`: it documents *some* of these patches and omits others entirely (both telephony patches, all three branding patches, `libselinux-pkgdir-uid-aliasing.sh`, `endospore-ams-account-reload.sh`, and every Trebuchet patch but one). Where it carries an operational warning a script does not, that warning is still worth having — it is usually the cost of a lost build.

## The register

**Machine-checked form (`NWP-20261020-04`).** `editions/endospore/build/patch-markers.tsv` is the Verify column's artifact checks as data: for each patch applied by `build-device.sh`, a literal the patch writes and the artifact (found by basename) that must hold it, a stock `control` literal, an `absent` original, or an `exempt` line giving the reason there is none. `build-device.sh` runs `check-patch-markers.py` on the artifact its build-number assert just read (the target-files zip, or the product tree of a dev image build) and refuses to reach signing unless it passes; CI runs `--self-check`, which holds the table to the scripts (every applied patch has a row, every literal is in its script and in no other applied script). A marker must be specific to ONE patch: a Nowhere-only token and a text no other applied script contains, which is why `com.nowhere.chooser`, inserted by two patches, is not one. Where the table and this register disagree about a literal, the script wins. **THE ONE RULE now includes a table row or an `exempt` line for every new patch**: a new patch is not done without one.

## Why a framework patch at all

Patching a tree we do not own is the last resort, and every entry below the register is expected to say what was tried first. This section collects those dead ends, because the cost of re-attempting one is a build cycle and, twice, a shipped defect. The failures fall into recurring shapes.

**The cache that is never re-read.** `SettingsProvider` builds a user's ssaid state when the user is created, caches it in `system_server`, and thereafter only ever *writes* the file. Seeding `settings_ssaid.xml` is therefore inert at every point in a login: seeding at roam-in reports `SKIPPED (state already live)`, and seeding between `createAndManageUser` and `startUserInBackground` logs OK and changes nothing — the id still rotates. Measured on lynx 2026-07-28, the write lands one second after the read that clobbers it. `AccountManagerService` is the same shape: it holds `UserAccounts` and its SQLite connection in-process and never re-reads them, so a roam that lays down restored account databases underneath it is invisible and the session reports `Accounts: 0`. Both were fixed by patching the *mint* — hand the framework the value at the moment it asks for one, instead of racing a file it may already have read.

**The race you cannot win.** `RestartDozeListener` issues an explicit `goToSleep`, and an explicit `goToSleep` **overrides wake locks** — so the chooser could only ever wake the screen afterwards and hope. Three slices tightened that race (fixed +6s repair → 1500/300ms poll → 300/100ms poll) and the clock was still filmed. On the account side, stripping stale `auth_uid_for_type` rows *after* `getUserAccountsNotChecked` was six milliseconds too late: `01:15:17.098` the account is deleted, `01:15:17.104` the strip logs success. A race cannot be tuned to zero; the patch removes the event or moves the work before the construction that consumes it.

**There is no read.** GrapheneOS's `GosPackageState` has no shell read at all — `edit-gos-package-state` is the only `pm` entry point and every verb is a write, device-proven on lynx as `cmd package get-gos-package-state` → `Unknown command`, rc=255 — and the binder read is gated by a hardcoded appId table with no signature and no device-owner door. `keystore2` is the same: there is no way to ask it whether a namespace holds any keys, because `listEntries` is gated on the caller *owning* the namespace by construction. Both were answered by patching the daemon. Note the deliberate rejection of the obvious alternative in the second case: a new AIDL method means a new interface, a new permission and a SELinux hole from a shell domain into the keystore domain, to carry a boolean the chooser only needs in order to paint a switch.

**The API exists and is scoped to the wrong caller.** `migrateKeyNamespace` forces an `APP` destination to the *calling* uid, so only an app can migrate a key into its own namespace — a daemon never can. `NfcService` grants reader mode only to the ActivityManager-foreground app or SystemUI, and only recomputes discovery while the screen is unlocked; the cold-resume gate is neither, and the chooser's app-side attempt to re-arm from the keyguard-dismiss callback fails because the cold-resume keyguard flaps and the grant only arrives tens of seconds later, when it is useless.

**An overlay cannot reach it.** An RRO cannot change a manifest *attribute* — that rules out the Trebuchet `configChanges` fix and the framework `android` package's `android:label`, which is a literal, not a `@string` ref. An RRO cannot branch on user, which is why `FallbackHome` had to be patched rather than styled: the `#160` overlay applies to the Settings APK and therefore to user 0 and every roamed user identically. An RRO cannot add Java logic, which covers both media-progress rings. There is no resource behind a hardcoded Kotlin default, which covers `addIconToHome`. And `device_profiles.xml` uses Launcher3's *private* styleables under `res-auto`, which an auto-generated RRO resolves to the overlay package, producing `aapt2: attribute … not found`. Adjacent, and worth keeping: `PRODUCT_ENFORCE_RRO_TARGETS := *` converting a static overlay into an auto-generated RRO was investigated and is **not** a cause of anything — the overlay pipeline was fine.

**The flag exists and is the wrong flag.** Enabling AOSP's `enforceSubscriptionUserFilter` looks like the clean fix for the SIM picker and is not: because the unbound sub is pinned to user 0, the gate would count as having its own sub and would lose sight of the bound physical SIM. `config_disableLockscreenByDefault=true` was not argued about — it was built, flashed and measured, and 3 of 4 boots still showed the clock. Making the gate `directBootAware` is blocked outright, because the gate keeps CE-backed state including `owner.conf`.

**The fallback that only exists on userdebug.** The stale-account-meta strip was originally a `sqlite3` shell-out from roamd. `sqlite3` does not exist on a `user` build, so on every shipping image the strip silently never ran and the roamed Google account was destroyed seconds after placement — for weeks, captured only because the device's own issue reporter printed `sqlite3: inaccessible or not found`. That fallback was deleted rather than repaired, with the reason recorded in roamd itself: *a fallback that only works on userdebug is the disease, not a safety net*. Doing the strip in-process, under the same locks and with the same `AccountsDb` methods `validate` itself uses, works identically on every build type.

**Compile-time gating.** The platform app create/unlink neverallow is verified against a platform-only policy — plat public + private, no system_ext, no vendor — so a type declared in our system_ext vendor dir fails there with `unknown type nowhere_media_file`. The type has to be promoted platform-side to be nameable in the exemption. Related and load-bearing: do **not** assume the build catches a neverallow violation. `NWP-20260825-09` device-proved twice on lynx that `sepolicy_filter_neverallow` **strips** a violating system_ext allow from the compiled CIL instead of failing — a green build that carries nothing, and nothing warns you. Grep the built CIL.

**What the patches cost, and why the discipline above is not ceremony.** Every patch here is an edit to a tree that is re-synced, re-anchored by upstream, and unversioned relative to this repo. Almost none is asserted in the built artifact. The failure mode is uniform and quiet: the producers keep logging success and the image ships without the behaviour. It has happened repeatedly — `#210` and `#112` missing from every canonical Endospore image until 2026-08-22, proven by `SettingsProvider.apk` carrying zero occurrences of `nowhere-ssaid-seed` on lynx 2026082104 while all three producers logged OK; `keystore-roam.sh` applied only by hand until 2026-08-30; `libselinux-pkgdir-uid-aliasing.sh` shipping a version of *itself* that anchored on the wrong function, reported success, left every marker it greps for present, and broke the build 157 steps later; `frankel` build 2026080600 published on beta carrying the uid-aliasing bug. Two structural mitigations came out of that: `build-device.sh` now names its cross-edition patches explicitly and **fails the build** on any non-zero patch, and the patches that can are expected to be idempotent *and* to exit non-zero when their anchor has moved. Neither mitigation covers a script that cannot fail — `endospore-brand-strings.sh` and `endospore-attest-strings.sh` exited 0 when their anchor had moved (as did `recovery-rebrand.sh`, `launcher3-grid.sh` and `launcher3-qsb-firstscreen.sh`, until `NWP-20261011-15` and `NWP-20261013-29` gave each an asserted end state that exits 2 with a `DRIFT:` line) — and neither covers a patch nothing runs. That is what the register is for.

## The patches

### ssaid-userkey-seed.sh

`editions/diaspore/build/patches/ssaid-userkey-seed.sh`

**Patches** `frameworks/base/packages/SettingsProvider/src/com/android/providers/settings/SettingsProvider.java` — `SettingsProvider.generateUserKeyLocked()`, called lazily from `generateSsaidLocked()`. The anchor is one line:

```java
final String userKey = HexEncoding.encodeToString(keyBytes, true /* upperCase */);
```

**Work ID** `DIA-20260728-09`, commit `7786463` ("#210 SSAID roaming — mint the userkey from a staged seed (framework patch)"), confirmed by `git log --follow`; the file has not been touched since. The script body carries no work ID of its own — it cites issue **#210** throughout, and `DIA-20260728-08` for the roamd-side companion.

**Scope.** Both editions. The script is tree-agnostic (`ssaid-userkey-seed.sh`'s "Tree-agnostic (the anchors are stock AOSP, unchanged in GrapheneOS)" header comment, ~:35) and lives in the Diaspore patches dir only because it was written there first — `editions/endospore/build/build-device.sh`'s comment "The Diaspore-dir patches this script applies … live there because they were written there first" (~:190-192) says exactly that. Automated application is **Endospore-only**: `build-device.sh` (~:220) names it in `GOS_MANDATED_PATCHES="sepolicy-app-media-manage.sh keyguard-roaming-noocclude.sh ssaid-userkey-seed.sh keystore-roam.sh sms-raw-no-sim-filter.sh system-userdir-guard.sh systemui-no-restart-doze.sh"` and applies it to every Endospore device. **No Diaspore build script applies it** — `grep -rn` across `editions/` and `ci/` finds no other caller — so on a LineageOS tree it is a manual build-host step, per AGENTS.md. Not device-specific.

**Why it exists.** An app's ANDROID_ID (SSAID) is not stored identity, it is *derived*: `SSAID = f(per-user "userkey", app signing certificate)`. Every login builds a **new** Android user, and Android mints that user a **random** userkey, so every app recomputes a brand-new id. The user-visible symptom, stated in the header: device-identity-bound sessions — "Amazon MAP et al." — log out on every single login. Carrying the one userkey row reproduces *every* app's id: no per-app rows, and no uid remapping (uids do not even exist yet at roam-in).

**Why it has to be a framework patch.** Seeding the `settings_ssaid.xml` **file** cannot work at any time. SettingsProvider instantiates the per-user ssaid `SettingsState` when the user is created, caches it in system_server, and **never re-reads the file** — it only writes it. Proven on lynx 2026-07-28: `12:19:24.351 SettingsState: No settings state /data/system/users/11/settings_ssaid.xml` against `12:19:25 [roamd] seedssaid OK user 11 (#210)` — the write lands one second too late and is clobbered by the cached (empty, therefore randomly minted) state. Two attempts died there: seeding at roam-in ("SKIPPED (state already live)"), and seeding between `createAndManageUser` and `startUserInBackground` (logged OK, had no effect — the id still rotated). Patching the **mint** has no race at all: `generateUserKeyLocked` runs lazily the first time any app in that user asks for its id, well after login, so the framework is handed the value at the moment it asks for one rather than being raced for a file it may already have read.

**What it changes.** The one anchor line is replaced with a block — via `awk`, not `sed`, because the block is multi-line and carries slashes, quotes and ampersands that sed's replacement syntax would mangle. Mechanically: `userKey` loses its `final` so it can be overridden; the code opens `/data/system/users/<userId>/nowhere-ssaid-seed`, reads up to 80 bytes into a `byte[80]`, trims, and if the content matches `[0-9A-Fa-f]{64}` uses it upper-cased (`Locale.US`) as the userkey and logs `Slog.i` "nowhere: seeded ssaid userkey for user &lt;id&gt; (#210)". Malformed content logs `Slog.w` and falls through to the stock random key; `FileNotFoundException` is caught silently (stock behaviour for user 0, the gate, and any non-roamed user); any other exception logs `Slog.w` and mints random. A `finally` block **always** deletes the seed file — consumed, malformed, unreadable or absent — making it strictly one-shot, so a stale seed left by a reaped user can never be replayed onto a recycled user id. Every type name is fully qualified (`java.io.*`, `java.nio.charset.*`, `java.util.Locale`) precisely so the patch adds no import hunk; an import hunk would be a second anchor to rot.

**Lands in `SettingsProvider.apk`, which ships in `/system/priv-app` — reflash the SYSTEM partition.** The script states this itself (`ssaid-userkey-seed.sh`'s "Lands in SettingsProvider.apk (/system/priv-app), so after building, reflash the SYSTEM partition" header comment, ~:38), and AGENTS.md repeats it.

**Idempotent.** Yes. First action is `grep -qF nowhere-ssaid-seed` on `SettingsProvider.java`; if present it prints `[ssaid-seed] SettingsProvider already patched -- skipped` and exits 0. If the marker is absent but the anchor is *also* absent it exits 1 with "anchor not found ... upstream changed generateUserKeyLocked, patch by hand". The rewrite goes to `$SP.nowhere.tmp` and is only `mv`d over the original after the marker is confirmed present in the temp file, so a failed rewrite never leaves a half-written source file behind. ⚠ **The anchor must match exactly once (`NWP-20261016-33`):** the script counts whole-line matches (`grep -cxF`) and refuses — exit 1, `SettingsProvider.java` untouched, no temp file — on zero ("anchor not found") or more than one ("anchor matched <n> times"), because the awk replaces only the first and a second site would keep minting a random userkey under a success exit. A refusal stops an Endospore build (`GOS_MANDATED_PATCHES`).

**If it is not applied.** The build does **not** break — the change is purely additive to a framework class. The feature degrades silently: any seed roamd stages is ignored and the stock random userkey is minted (pre-#210 behaviour, no breakage), so every app's ANDROID_ID rotates on every login and device-bound logins drop. `build-device.sh`'s "THEY WERE NOT APPLIED AT ALL UNTIL NWP-20260822-08" comment (~:195-202) calls this out as failing "SILENTLY AND EXPENSIVELY": roamd logs `seedssaid staged 64 chars`, the daemon logs `seed-ssaid -> OK`, the chooser stays quiet, and an unpatched SettingsProvider mints a random userkey anyway.

**Verify.** logcat: `nowhere: seeded ssaid userkey for user <N> (#210)`, emitted by the first app in that user to ask for its id, cross-checkable against roamd's staging line — in-tree at `core/vendor-common/bin/nowhere_roamd.sh` ~:7426, `[roamd] seedssaid staged ${#_uk} chars user $uid (#210)`. Static check on the **built** image: `grep`/`strings` `SettingsProvider.apk` for `nowhere-ssaid-seed`. `build-device.sh`'s "Device-proven absent on lynx 2026082104" comment (~:201-202) records the negative case device-proven on lynx build 2026082104, where `SettingsProvider.apk` carried 0 occurrences while all three producers logged success. Source-side: the same grep against `frameworks/base/.../SettingsProvider.java`.

**Warnings.**

- ⚠ roamd must **still** remove a stale `settings_ssaid.xml` left behind by a recycled user id (`DIA-20260728-08`). If that file exists, SettingsProvider loads a userkey from it, `generateUserKeyLocked` is never called, and the seed is never consumed.
- ⚠ Every Endospore image before `NWP-20260822-08` was missing this patch (and #112) unless a human ran it by hand: the build loop globbed only the two endospore dirs. The patches are now named **explicitly** rather than globbed, because the Diaspore patches dir also holds Trebuchet (LineageOS launcher) patches that must not be applied to a GrapheneOS tree, which uses Launcher3.
- ⚠ `build-device.sh`'s "A FAILED PATCH NOW FAILS THE BUILD" comment (~:226-229): a failed patch now **fails the build**. It used to print FAILED and carry straight on through signing and web-packaging.
- The seed is one-shot by design (deleted whether consumed, malformed or unreadable); an absent seed is byte-for-byte stock behaviour.

No Diaspore build script applies it either (the only matches outside the script are `build-device.sh`, `docs/` and backlog rows), so on a LineageOS tree it remains a manual build-host step.

**Why it exists.** #210 part 1 (SSAID) was necessary and **not sufficient**. The stated symptom: "Amazon still signs out on every login". MAP seals its token under Keystore keys (aliases `IDENTITY_MAP_KEYSTORE_ALIAS`, `mshop_rcs_master_key`, `widget_cache_key`, observed on lynx), and keystore entries are namespaced by app uid, so they are deleted with the roamed user. The carry is possible at all because — verified in-tree, not assumed — the TEE has **no concept of Android users**: a KeyMint blob is device-bound, not uid-bound, and ownership is pure sqlite bookkeeping (`Domain::APP => KeyDescriptor{nspace: caller_uid.0}`); and `Enforcements::super_encryption_required` returns `None` unless a key is auth-bound (`UserSecureID`), `UnlockedDeviceRequired`, or boot-level, so Amazon's `NO_AUTH_REQUIRED` keys are raw KeyMint blobs, carryable as bytes. §8 adds a second reason: the chooser's "Keep me signed in" switch was offered on every kept non-Google app and was **inert for most of them** — Chester, 2026-08-25: *"not have this option unless its something similar to Amazon as the current setting is misleading/invalid"* — so keystore2 writes a census of which app namespaces have ever held a key.

**Why it has to be a framework (daemon) patch.** Two independent reasons, both stated in the script.

*The carry:* `migrateKeyNamespace` already exists, but it forces an APP destination to the **caller's** uid (`maintenance.rs migrate_key_namespace` → `database.rs`), so only the app itself could migrate a key into its own namespace — a daemon cannot. And parking keys in a SELINUX namespace only survives while `/data` does, while boot-wipe (P2) is mandatory in the lock model, so only a store-backed bundle outlives what the OS is committed to becoming.

*The census:* there is no way to ask keystore2 "does namespace N hold any keys". The AIDL surface is per-caller by construction — `listEntries` is gated on the caller **owning** the namespace (`check_key_permission(KeyPerm::GetInfo)` against the caller uid), with no device-owner door and no signature door. The script names this as the same shape as the GosPackageState read problem in `NWP-20260821-17`, with the same answer: patch the daemon. A `0644` file under `keystore_data_file` was chosen over a new AIDL method because a new call means a new interface, a new permission and a SELinux hole from a shell domain into the keystore domain — for a boolean the chooser only needs in order to paint a switch — and `endospore_priv` already holds read on that type, so the census needs no sepolicy change at all.

**What it changes — export.** On `clear_namespace` (the **primary** hook: a roamed app is uninstalled during the reap, which lands here *before* the bulk `remove_user`, so this is where its keys actually die) and, as a fallback, on `SuperKeyManager::remove_user`, `nowhere_dump_user_keys` SELECTs the user's `Domain::APP`, `KeyType::Client`, `KeyLifeCycle::Live` `keyentry` rows plus their `keyparameter`, `keymetadata`, `blobentry` and `blobmetadata` rows — hex-encoded, with the sqlite `typeof()` tag preserved so the import round-trips integers, text, blobs and nulls exactly (`security_level` is cast to text so the shared extractor does not hit "Invalid column type Integer" — `DIA-20260728-18`). Only **carryable** keys: the SQL excludes any key having a `blobmetadata` row with `tag = 0` (`BlobMetaEntry EncryptedBy`), i.e. superencrypted under the old user's LSKF-derived super key. Each namespace's rows are written as a v1 line-based bundle to `/data/misc/keystore/nowhere-export/<ns>.keys`, mode `0600`, headed by `v1` / `unit <device-unit-id>` / `ns <n>`; roamd pushes these as the `#keys` scope after the reap. `NWP-20260830-03` inverted the meaning of an empty `keep` slice from *none* to *every namespace of the user* — that inversion **is** the always-carry change; `export_for_namespace` still passes a single-element slice, so it is unaffected.

**What it changes — import.** Three call sites into two functions.

1. `service.rs` `get_key_entry` imports **eagerly** before the lookup for `Domain::APP`, and **again on a miss**, retrying the lookup once (the load closure was factored out and `super_key` cloned so it stays `Fn` and can run twice). Both call `try_import`, which reads `/data/misc/keystore/nowhere-import/<ns>.keys` and is **whole-bundle one-shot**: the file is removed immediately after the read, whatever happens.
2. `security_level.rs` `generate_key` calls `nowhere_import_on_create`, which asks `try_import_create` for exactly this `(namespace, alias_hex)`, imports that **one** key, and consumes just that alias's rows via `consume_alias` — the file is **rewritten** with those rows dropped, and deleted only when the last `key` row goes (a parse rejection also deletes it, so a bad bundle is rejected once and never retried). Per-alias, not whole-bundle, because an app creates its aliases at different times.
3. `nowhere_import_keys` re-inserts the rows through `insert_with_retry`, remaps `blobmetadata` onto the **new** `blobentry` ids (an orphan `bm` row refuses the whole import), binds the alias as a UTF-8 `String` (TEXT), and first UPDATEs any existing row holding that alias to alias/domain/namespace NULL + state `Unreferenced` — exactly like the stock `rebind_alias` — propagating the row count into `.do_gc(need_gc)`.

`parse_bundle` vets everything: it rejects a bundle not stamped `v1`, one carrying no device stamp, one stamped for a different device, and any `bm` row with `tag 0`. An internal `ns` mismatch is deliberately **not** a rejection — the app is reinstalled every roam and gets a fresh appId, so the ns always drifts, and rejecting on it refused *every* carried bundle.

**What it changes — census (§8–11).** `note_app_key` is append-only over a process-global `Mutex<HashSet>` (KeystoreDB is thread-local, so a per-DB set would re-append once per binder thread), writes one decimal uid per line to `/data/misc/keystore/nowhere-ns-keys` mode `0644`, and inserts into the set only **after** the append lands. It is hooked into `create_key_entry_internal` (the single choke point, after the domain gate, before the INSERT) and into `nowhere_import_keys`. `bootstrap()`, hooked into `globals.rs` `DB_INIT.call_once`, unions the file with a `DISTINCT` namespace scan (`nowhere_app_namespaces`, deliberately **not** filtered by `key_type`) and rewrites the file sorted via tmp+rename, so it is a derived **view** that self-heals rather than a cache that drifts. Uids only, never package names.

**Lands in `keystore2` — a Rust binary in `/system/bin` — so the SYSTEM partition must be reflashed.** ⚠ The script itself never states this. The claim comes from AGENTS.md ("lands in keystore2 (a binary in /system/bin) → system reflash") and from `docs/ondemand-sandboxed-play-group.md:~369`: "Part 3 is roamd (/system/bin, hot-patchable); parts 1-2 are keystore2 and need the flash." No `services.jar`, no APK, no sepolicy.

**Idempotent — at the same version only; it deliberately refuses across versions.** The gate: if `database.rs` contains the marker `nowhere_dump_user_keys` **and** the current `PATCH_VERSION` (`NWP-20260830-03`) it prints "already patched (NWP-20260830-03) -- skipped" and exits 0. If the marker is present but the version is not, it exits 1 with "tree carries an OLDER keystore-roam patch" and the exact revert command:

```

```

Re-applying cannot work regardless, because every step is a textual replace against **pristine** anchors; skipping instead of failing would silently ship a build without the newer fix (the #108 class of bug). Note that the later sections' own guards are **not** benign skips: §8/§9/§10/§11 use `sys.exit('<message>')`, which is exit code 1, and the shell runs under `set -euo pipefail` — so a half-patched tree that trips one of them **aborts the whole script**. That is only reachable in an already-inconsistent tree, since the top gate exits first. The script ends with six greps plus an assertion that `PATCH_VERSION` was actually stamped into `database.rs` — because a bumped-but-unstamped version would make the gate refuse to run on a tree it had itself just patched, self-bricking every later build with a message pointing at the wrong problem.

**Warnings.**

- ⚠ **It refuses to re-apply over an older copy of itself, by design.** Revert `keystore2/src/` and delete `nowhere_roam.rs` first. The script, AGENTS.md and `docs/ondemand-sandboxed-play-group.md` all repeat this; that doc records it as one of "two traps this exposed... both would have wasted a build".
- ⚠ **Safety posture** (`nowhere_roam.rs` module doc): everything here is best-effort and must never fail a user removal. Every entry point swallows its errors after logging, because losing an export costs the carry-over, while an error escaping `remove_user` would break user deletion — a core amnesia guarantee.
- ⚠ **Superencrypted blobs** (`BlobMetaEntry EncryptedBy`, tag 0) are refused on export **and again** on import (defence in depth), because a restored one yields a key that **exists but cannot be used** — apps handle that far worse than a missing key (`InvalidKeyException`, often with no re-login path).
- ⚠ **The unit id must live at `/data/misc/keystore/nowhere-unit-id`.** keystore2 runs as the `keystore` UNIX user, not root, so `/data/nowhere/unit-id` (root:root 0600, `nowhere_data_file`) is unreachable: `read_unit()` silently returned `""` there and **every export no-op'd** (`DIA-20260728-17`).
- ⚠ **The alias must bind as TEXT, not BLOB.** `keyentry.alias` has BLOB affinity but no coercion, and SQLite never equates a BLOB to a TEXT, so a blob-bound alias made every lookup miss → `KEY_NOT_FOUND` → `generate_key` minted a fresh key that shadowed the carried one, every roam (`DIA-20260730-01` — the root cause of "app signs out on every roam").
- ⚠ **There is no UNIQUE constraint on `(domain, namespace, alias)`.** A bare insert next to a key the app already minted leaves **two** Live rows, and every later lookup dies in `with_rows_extract_one` ("Unexpected row" → `SYSTEM_ERROR`), which the app reads as a corrupt vault and answers by regenerating and signing the user out — the exact failure the carry exists to prevent. Hence the unreference-then-insert (`DIA-20260803-02`).
- ⚠ **Anchoring on a bare signature steals the preceding function's `///` doc block** and fails the crate's `deny(missing_docs)` three minutes into a build. It happened twice (§3, and again on 2026-08-26), so both insertion sites walk back over the contiguous `///` lines and §9 asserts the doc blocks stayed attached.
- ⚠ **Section order is load-bearing:** the `globals.rs` bootstrap must land before the `database.rs` hooks, because those hooks carry `PATCH_VERSION` and the staleness gate greps `database.rs` for it.
- ⚠ Requires `python3` on the build host (nine inline `python3` heredocs).

### endospore-ams-account-reload.sh

`editions/endospore/build/patches/endospore-ams-account-reload.sh`

**Patches two files under `frameworks/base/services/core/java/com/android/server/accounts/`:**

- `AccountManagerService.java` — adds two package-private methods, `detachUserAccounts(int userId)` and `reloadUserAccounts(int userId)`, inserted immediately before the `@VisibleForTesting void onUserUnlocked(Intent intent)` anchor. **Work IDs.** `DIA-20260802-05` (the id stamped in the injected code) / `DIA-20260802-08`, commit `266af2a` ("formalize the sandboxed-Play-roam framework patches as endospore patch-scripts"), then `DIA-20260817-01` commit `6b67398` ("#732: no sqlite3 anywhere -- five userdebug-only call sites replaced") and `DIA-20260818-02` commit `b3048f8` ("#732: strip stale auth-uid meta BEFORE UserAccounts is built"). All three confirmed by `git log --follow`. Issue: **#732**; the device-side issue report it cites is `NW-f73faa55d1da`.

**Scope.** Endospore only as wired today. It lives in `editions/endospore/build/patches/` and is picked up by `build-device.sh` (`for p in $PATCH_LIST` loop, ~:223)'s `"$REPO"/editions/endospore/build/patches/*.sh` glob, i.e. every Endospore device (lynx, stallion, …). Nothing in the Diaspore build applies it. The script header labels it "nowhere/endospore"; `editions/endospore/README.md:68` lists it as an OS-level (not per-device) patch. ⚠ It is **not mentioned anywhere in AGENTS.md**.

**Why it exists.** The amnesiac roam restores the user's account databases (`/data/system_ce|de/<uid>/accounts_ce|de.db`) **underneath** AccountManagerService's open connection; AMS caches the empty snapshot it read at unlock and never re-reads it. The user-visible symptom, from the header: "the roamed account db is on disk but AMS keeps serving the empty snapshot (Accounts: 0)" — the signed-in Google account does not survive a login. The second, worse problem (#732): the roamed `accounts_de.db` carries `auth_uid_for_type` rows minted under the **previous** session's app ids, and `validateAccountsInternal` treats an unknown stored uid as an obsolete authenticator and **destructively deletes the account**. roamd used to strip those rows by shelling out to `sqlite3` — a **userdebug-only** binary — so on every `user` build the strip silently never ran and the roamed Google account died seconds after placement. Captured verbatim by the device's own issue report: `sqlite3: inaccessible or not found`.

**Why it has to be a framework patch.** AMS holds the `UserAccounts` object and its SQLite connection in-process and re-reads neither; nothing outside system_server can make it drop and reload them, so the roam daemon has no lever at all — hence two new shell/root-only entry points on the service itself. Beyond that, the **strip** must happen inside the framework and **before construction**: `getUserAccountsNotChecked` validates *on construction* (`if (accounts == null) { accounts = new UserAccounts(...); ...; validateAccounts = true; }`), and `detachUserAccounts` — which the roam necessarily calls first so the db can be swapped — removes the cached entry, guaranteeing that construction path every time. The first attempt stripped **after** `getUserAccountsNotChecked` and was six milliseconds too late, measured on lynx build 2026081611:

```
01:15:17.098  deleting account ... type com.google's registered authenticator no longer exist
01:15:17.103  validateAccountsInternal#Deleted UserId=12, AccountId=1
01:15:17.104  reloadUserAccounts: stripped 1 stale auth-uid mapping(s)
```

— cleaning up after the fact. Doing it in-process, with the same `AccountsDb` methods validate itself uses and under the same locks, also works identically on **every build type**, unlike the external `sqlite3` strip that only existed on userdebug.

**What it changes.** `AccountManagerService.java` gains:

- `detachUserAccounts(userId)` — gated to `Binder.getCallingUid()` in `{Process.ROOT_UID, SHELL_UID, SYSTEM_UID}` (`SecurityException` otherwise). Under `synchronized (mUsers)` it fetches and removes the cached `UserAccounts` and calls `AccountManager.invalidateLocalAccountsDataCaches()`, explicitly **not** touching `mLocalUnlockedUsers` (unlike `purgeUserData`, which would clear it and leave CE un-attached); then under `dbLock`/`cacheLock` closes the debug statement and the db. Logs `detachUserAccounts: closed + dropped cached accounts for user N`.
- `reloadUserAccounts(userId)` — same uid gate; then the #732 **pre-strip** straight on the DE database in the detached window: `AccountsDb.create(mContext, userId, preNDbFile, deDbFile)`, `findMetaAuthUid()`, `deleteMetaByAuthTypeAndUid()` for every entry, `close()` in a `finally`, all wrapped in `try/catch(Throwable)` that logs `Log.e` "PRE-STRIP FAILED ... validate may delete the roamed account (#732)" — deliberately non-fatal and loud. Because `TABLE_META` is then empty, `validateAccountsInternal`'s `obsoleteAuthType` loop body never runs, nothing is marked obsolete, and no account is deleted; validation then repopulates the meta with the **current** authenticator uids, which is the self-healing property. After that: `getUserAccountsNotChecked(userId)` (re-creates, so it re-reads DE and — since the user is still flagged unlocked — CE); a second belt-and-braces strip under `dbLock`/`cacheLock` for anything validation re-added that is already stale (appIds drift between materializes); `validateAccountsInternal(accounts, true)`; `AccountManager.invalidateLocalAccountUserDataCaches()`; `sendAccountsChangedBroadcast(userId, null, "roam-reload")`; and the log `reloadUserAccounts: re-read on-disk accounts for user N`.

`AccountManagerServiceShellCommand.java` gains the two verbs (`cmd account detach-user <uid>` / `cmd account reload-user <uid>`), a positional user-id parser that prints `Error: bad user id '<arg>'` on a `NumberFormatException`, and two `onHelp` lines describing both as "(roam internal)".

**Usage contract** (roamd, `nowhere_roamd.sh` `acct_reload`, ~:5696-5727): bracket the db placement — `detach-user`, lay the restored dbs down, `reload-user` — so the swap happens while the connection is closed. Otherwise a close-time WAL checkpoint clobbers the restored rows.

**Lands in `services.jar` — a full `m`, and a SYSTEM partition reflash.** ⚠ This is **inferred**, not stated: `AccountManagerService` and its shell command live in `frameworks/base/services/core`, but the script does not say where it lands, and AGENTS.md does not document this patch at all. It is the same class as the other `frameworks/base/services` patches AGENTS.md *does* describe (`gos-chooser-grant.sh`, `keyguard-roaming-noocclude.sh`), which it explicitly places in `services.jar`.

**Idempotent.** Yes, and in three modes for the AMS file. If the source already contains the string `pre-strip removed ` it prints "already patched (with the #732 PRE-strip) -- skipped" and exits 0. If it contains `void reloadUserAccounts(int userId)` but not the pre-strip, it performs a **version-agnostic upgrade**: brace-matches the whole existing method and replaces it with the canonical body taken from the same `methods` blob the fresh-install path uses. (Round 1 keyed on one exact previous body and aborted the moment a second revision existed; this keeps one source of truth.) Otherwise it inserts at the anchor, exiting 2 with "ANCHOR NOT FOUND (upstream changed?)" if the anchor or the brace match is gone. The ShellCommand file skips (exit 0) if `runReloadUser` is present, and each of its three replacements aborts with exit 2 if its anchor is missing. Requires `python3`.

**If it is not applied.** No build break — both edits are additive. It degrades silently and **destructively**, in two ways.

1. `cmd account detach-user` / `reload-user` simply do not exist, and roamd's invocations redirect stdout and stderr to `/dev/null` (`nowhere_roamd.sh` `acct_reload`: `cmd account detach-user` ~:5699 and `cmd account reload-user` ~:5727), so they fail unnoticed. AMS keeps serving the empty cached snapshot — the restored account dbs sit on disk while the session shows `Accounts: 0`.
2. ⚠ **There is no longer any fallback strip.** `DIA-20260817-01` deleted roamd's `sqlite3` shell-out and states the reason in-tree — "No shell-side fallback on purpose: a fallback that only works on userdebug is the disease, not a safety net" (`nowhere_roamd.sh` `acct_reload`, the comment ending "No shell-side fallback on purpose", ~:5718-5725). So on an unpatched build **nothing** clears the stale `auth_uid_for_type` rows, and `validateAccountsInternal` destroys the roamed Google account whenever AMS next constructs `UserAccounts` for that user. With an **older** version of the patch present (pre-`DIA-20260818-02`), the same destruction happens on construction — that is the weeks-long silent account loss of #732.

**Verify.** logcat, at roam placement:

```

reloadUserAccounts: pre-strip removed <n> stale auth-uid mapping(s) before UserAccounts construction (roam #732)
reloadUserAccounts: stripped <n> stale auth-uid mapping(s) before validate (roam #732)   [optional]
reloadUserAccounts: re-read on-disk accounts for user <N>
```

The absence/regression tell is the AMS pair `deleting account ... registered authenticator no longer exist` followed by `validateAccountsInternal#Deleted UserId=<N>, AccountId=<n>`. Behavioural: `cmd account` help lists `detach-user` / `reload-user`, and the roamed Google account is present in the new session after login. Source-side: grep `AccountManagerService.java` for `pre-strip removed ` and `AccountManagerServiceShellCommand.java` for `runReloadUser`.

**Warnings.**

- ⚠ **Order is load-bearing:** roamd must detach **before** replacing the files, or the close-time WAL checkpoint writes over the restored rows; reload only after placement.
- ⚠ `detachUserAccounts` must **not** touch `mLocalUnlockedUsers` — `purgeUserData` does, and that would leave CE un-attached on reopen.
- ⚠ Both verbs are shell/root/system only, and `reload-user` is called exactly once per roam placement, never on a db whose meta is live truth. The strip is safe only because of that.
- ⚠ The pre-strip failure path is intentionally non-fatal and loud: "a roam that cannot strip is exactly the situation that silently destroyed accounts for weeks, so it must not fail quietly again."
- ⚠ **AGENTS.md gap:** unlike every other framework patch in this cluster, this one is not documented in AGENTS.md's *Building & Verifying* list at all. Its only wiring and doc references are `editions/endospore/README.md:68`, `docs/sandboxed-play-roam.md`, `core/vendor-common/bin/nowhere_roamd.sh` (`acct_reload`, ~:5690-5727) and `core/vendor-common/src/nowhere_db_fix.c`.
- The second (post-construction) strip is belt-and-braces only; the **pre-strip** is what actually prevents the deletion.
- `build-device.sh`'s "A FAILED PATCH NOW FAILS THE BUILD" comment (~:226-229): a failed patch now fails the build, so a drifted anchor here stops the build rather than silently shipping an image without the behaviour.
- ⚠ **Until `NWP-20261004-01` the detach did NOT close the CE database.** `detachUserAccounts` calls `AccountsDb.close()`, which on Android 17 closed only the DE helper, so the CE connection stayed open while roamd replaced `accounts_ce.db` under it — the very clobber the order rule above exists to prevent. `endospore-accountsdb-close-ce.sh` (next section) is what makes the bracket close both files.

### endospore-accountsdb-close-ce.sh

**Work ID.** `NWP-20261005-22` (backlog §B, "A COLD-LOCKED PHONE SHOWS THE ROAMED IDENTITY'S GOOGLE EMAIL IN PLAINTEXT"; the trace is `NWP-20261005-20`, the sync cost `NWP-20261005-21`).

**Why it exists.** A cold lock stops the user, and AMS closes its databases at `onUserStopped`. Within 236 ms (lynx `2026100503`), SyncManager's `ACTION_USER_STOPPED` handler runs `updateRunningAccountsH`. Its cleanup calls `getAllAccountsForSystemProcess()` over every alive user, and `removeStaleAccounts()` calls `getAccounts(userId)` for each. A user the stop found unloaded gets no snapshot and behaves as before. On its own this moves no file: roamd's seal of `accounts_de.db` at the lock and its restore at resume depend on it.

**Verify.** logcat at a cold lock: `AccountManagerService: onUserStopped <n>` followed by `nowhere: snapshot <k> account(s) of stopped user <n> (NWP-20261005-22)`. The root cause is by-design Android behaviour: `canShowWhenLockedInner` returns true for `mShowWhenLocked || a showWhenLocked window || an always-visible user`, and our roamed user is a normal `FULL_SECONDARY` (`alwaysVisible=false`, confirmed via `dumpsys user`), so the leak arrives through app-requested show-when-locked. ~~On an amnesiac phone nothing in a roamed session should ever be visible over the warm lock.~~ *(⚠ SUPERSEDED 2026-10-13 by `docs/product-decisions.md`, “2026-10-13 — DECIDED: an incoming call in a warm-locked session can be answered or declined from the lock”: the session's default dialer shows its in-call screen over the lock while a call rings or is in progress; nothing else in the session may.)*

**Why it was revised (`NWP-20261013-08`).** The #112 guard blocked the dialer's in-call screen too: on frankel (user build 0.5.46, 2026-10-13) Chester's warm-locked session rang for an incoming call on its own SIM, but the call could be neither answered nor declined — tapping it led to the unlock screen.

**Why it has to be a framework patch.** Stated in the header: Android lets any activity that requests `showWhenLocked` draw over the lock — permission prompts, navigation, alarms, incoming calls — and **there is no config toggle for it**. The roamed user is not an always-visible user, so no user-property or device-policy lever reaches this decision. The only door is the framework decision function, and the exemption has to be decided in the same place.

**What it changes.** Four blocks; the marker `nowhere-noocclude NWP-20261013-08` appears once per file.
- `ActivityRecord.canShowWhenLockedInner`, as its first statement: a secondary user's activity returns `false` unless its package equals that user's entry in `ActivityTaskManagerService.mNowhereInCallDialers`; if it does, the stock checks still decide (the Dialer's `InCallActivity.setWindowFlags()` adds `FLAG_SHOW_WHEN_LOCKED`, `packages/apps/Dialer/java/com/android/incallui/InCallActivity.java:269-285` in GrapheneOS 2026061600). User 0 — the gate — falls through to stock logic untouched and keeps its own `setShowWhenLocked`, which it needs to get past user 0's insecure swipe keyguard at boot and forced-wake. `canShowWhenLocked` is evaluated under the WM global lock (its keyguard callers are `KeyguardController.canShowActivityWhileKeyguardShowing` and `checkKeyguardVisibility`, `KeyguardController.java:400-437`, reached from `RootWindowContainer.ensureActivitiesVisible`; `ActivityClientController.setShowWhenLocked`, `:1663-1671`, re-evaluates under `synchronized (mGlobalLock)`), so this block only reads a volatile: no binder call, no other service's lock. The exemption is per PACKAGE: any show-when-locked activity of that dialer passes during a call (for example its pre-call screen during an active call), not only the in-call activity.
- `ActivityRecord.canShowWhenLocked`, in its `mInheritShowWhenLocked` branch, right before the stock `return activity != null && canShowWhenLockedInner(activity);`: the same package check on the INHERITING activity, failing closed. Without it, an activity of another package with `inheritShowWhenLocked` sitting above the dialer's in-call screen in its task would inherit the exemption and show over the lock during a call, which the #112 guard never allowed and the decision does not.
- `ActivityTaskManagerService`: `volatile Map<Integer, String> mNowhereInCallDialers` and the code that writes it. A `TelephonyCallback.CallStateListener`, held in a final field (`mNowhereInCallListener`) because TelephonyCallback's registry stub keeps only a `WeakReference` to it and drops an event once it is collected (`TelephonyCallback.java:2090-2094`, `:2145-2147`), is registered on the DEFAULT `TelephonyManager` (never `createForSubscriptionId`) and receives Telecom's consolidated call state: Telecom's `PhoneStateBroadcaster.updateStates` (`packages/services/Telecomm/src/com/android/server/telecom/PhoneStateBroadcaster.java:104-116`) computes RINGING if any call rings and OFFHOOK if one is dialing, active or held, and `TelephonyRegistry.notifyCallStateForAllSubs` (`frameworks/base/services/core/java/com/android/server/TelephonyRegistry.java:1780-1815`) delivers it only to default-subscription listeners. On RINGING or OFFHOOK it asks `RoleManager.getRoleHoldersAsUser(ROLE_DIALER, …)` for every non-system user (`UserManagerInternal.getUserIds()`), on `BackgroundThread` with no lock held, keeps a user only when exactly one holder answers, publishes the map, and only then takes `mGlobalLock` to call `notifyKeyguardFlagsChanged` on every display. Any other state publishes `null`, so the lock is back over a lingering in-call screen as soon as the call ends. Every failure leaves the entry, or the whole map, absent: the exemption fails CLOSED to the #112 behaviour.
- `ActivityTaskManagerService.Lifecycle.onBootPhase`: registers the callback at `PHASE_ACTIVITY_MANAGER_READY`. SystemServer dispatches that phase from `ActivityManagerService.systemReady`'s callback outside its lock (`ActivityManagerService.java:9867`), after `TelephonyRegistry` (`SystemServer.java:1653`) and `RoleService` (`:1714`) have started.

*Rejected for the exemption, and why:* (1) asking RoleManager or Telecom from inside `canShowWhenLockedInner` — a binder call, and the role or telecom lock, taken under the WM lock: a deadlock risk; (2) identifying the activity Telecom bound as the InCallService UI — that binding lives in ActivityManagerService's service records (the AMS lock, which ranks above the WM lock) or inside Telecom (a separate classloader with its own `SyncRoot` lock); (3) the audio mode (`MODE_RINGTONE`/`MODE_IN_CALL`) — VoIP apps set it too, so it is not a call signal; (4) a role-change listener that caches the dialer at all times — it would keep a map alive outside calls for no gain, where computing it only at a call-state change keeps the exemption empty while no call exists. *Accepted trade-off (the decision):* while a call rings or is in progress, any show-when-locked activity of that user's default dialer shows over the lock, which in practice is its in-call screen, and with it the caller's name from the session's contacts. The call state is device-wide, so during any call every secondary user's own dialer is exempt; only the foreground session's keyguard is showing.

Mechanically it is `set -euo pipefail` bash plus an inline `python3` heredoc on the model of `system-userdir-guard.sh`: every anchor in both files is counted before anything is written (drift → exit 2, nothing written), each file is written to a `.nowhere-tmp` copy and self-checked, and only then are both replaced.

### systemui-no-restart-doze.sh

**Patches** `frameworks/base/packages/SystemUI/src/com/android/systemui/flags/RestartDozeListener.kt`, the wake/sleep pair inside `maybeRestartSleep()` (called from `DreamMonitor.onStart()`), guarded by the secure setting `restart_nap_after_start` (`RESTART_SLEEP_KEY`).

**Why it exists.** `RestartDozeListener` exists to restore AOD across a SystemUI **restart**: it records the dozing state into `restart_nap_after_start` on every doze change, and 1000 ms after SystemUI starts it does `wakeUp()` + `goToSleep()` if the flag is set. On a normal phone that is invisible and correct — SystemUI crashed while dozing, so put it back. On Nowhere it is simply wrong: the device wipes at power-off and must always boot to a visible gate, and the flag survives from whenever the device last dozed, so the "restart" is really a **fresh boot being dragged back to sleep**. The user-visible symptom as stated: a freshly booted device flashes a full-screen lockscreen clock before the gate appears, which Chester filmed repeatedly. Device-measured on lynx 2026-08-25, build 2026082408: SystemUI starts ~01:08:50 and `PowerManagerService: Going to sleep due to application (uid 10166)` lands at 01:08:51.017 — 1000 ms later, uid 10166 = systemui, reason = application, all three matching this call exactly. ⚠ Read the warnings below before treating that as the cause of the clock; the record says it was not.

**Why it has to be a framework patch.** An explicit `goToSleep` **overrides wake locks**, so the chooser could only ever *race* it — wake up afterwards and hope the AOD clock had not faded in yet. Three slices tightened that race (NWP-20260823-05, -16, -18; the watcher went from a fixed +6 s repair, to a 1500/300 ms poll, to a 300/100 ms poll) and Chester still saw the clock, because a race cannot be tuned to zero. Removing the sleep is the only thing that makes the blink structurally impossible. Two further levers were tried and are recorded dead in worklog NWP-20260825-06: `config_disableLockscreenByDefault=true` was built, flashed and measured — 3 of 4 boots still showed the clock — and dropped; and making the gate `directBootAware` is **blocked**, because the gate keeps CE-backed state via `getFilesDir()`, including `owner.conf`.

**What it changes.** It replaces the body of the `if (settings.getBool(RESTART_SLEEP_KEY, false)) { … }` block: the `powerManager.wakeUp(...)` + `powerManager.goToSleep(...)` pair and the `"Restarting sleep state"` log are removed, leaving a single `Log.d("RestartDozeListener", "Nowhere: NOT restarting sleep state (NWP-20260825-03)")` plus five explanatory comment lines. The `if` and its settings read are **deliberately left in place** so the log line still proves the path was reached, and so no unreachable code is left behind (`systemui-no-restart-doze.sh`'s "The `if` is deliberately LEFT IN PLACE" header comment, ~:21-22). Mechanically it is `set -euo pipefail` bash plus an inline `python3` heredoc; `assert s.count(anchor) == 1` on the exact eight-line upstream block, aborting with `maybeRestartSleep shape changed, re-check the patch`.

**Lands in** SystemUI — an **APK in `/system_ext`** (stated outright in `systemui-no-restart-doze.sh`'s "Rebuilds SystemUI (an APK in /system_ext)" header comment, ~:26) → the **system_ext** partition must be reflashed. AGENTS.md and the `NWP-20260825-03` worklog row both state that a `system`-only flash leaves it stale. It is *not* `services.jar`, despite AGENTS.md loosely calling it "a framework patch".

**Scope and who applies it.** Tree-agnostic by the header ("the class is identical in LineageOS and GrapheneOS"), and AGENTS.md lists it as a patch to apply on the GrapheneOS tree. ~~⚠ **Nothing auto-applies it on either edition.** It is not in `GOS_MANDATED_PATCHES` (`build-device.sh` `GOS_MANDATED_PATCHES`, ~:220, names only `sepolicy-app-media-manage.sh`, `keyguard-roaming-noocclude.sh`, `ssaid-userkey-seed.sh`, `keystore-roam.sh`, `sms-raw-no-sim-filter.sh`, `system-userdir-guard.sh`), and it does not live in an endospore directory, so the `for p in $PATCH_LIST` glob (`build-device.sh`, ~:223) misses it; no Diaspore build script applies patches at all. ### `gos-chooser-grant.sh`

`editions/endospore/build/patches/gos-chooser-grant.sh` — **NWP-20260821-17** (Slice A, architecture A″; design `NWP-20260821-16`). Commit `f113374`, 2026-08-21, merged as PR #843 (merge `9ba0c6a`) from `nwp-20260821-17-gos-flags-roam`. Design of record: [`docs/gos-package-state-roam.md`](gos-package-state-roam.md) §6 "As built". Backlog row "Slice A — roam the GrapheneOS hardening flags", status NEEDS-DEVICE.

**What it patches.** `frameworks/base/services/core/java/com/android/server/pm/GosPackageStatePermissions.java`, the static `init()` method. The anchor is the *end* of the Settings-app grant — the literal `.apply(ksp.settings, computer);` followed by the blank line and the `userManager = Objects.requireNonNull(...)` assignment — chosen so the insertion keeps `settingsReadWriteFlags` in scope and puts the new grant beside the one it mirrors. Symbols the header reasons about but does **not** edit: `GosPackageStatePermission.filterRead()`, `checkCrossUserPermissions()`, `getProfileParentId()`, `createFull()`/`ALLOW_CROSS_ANY_USER_WRITES`, and `PackageManagerShellCommand`'s `edit-gos-package-state`.

**Why it exists.** GrapheneOS's per-app hardening switches (Settings › Apps › \<app\> › "Exploit protection compatibility mode" and its siblings) are `GosPackageState`, which is per-(package, user). Every Nowhere login mints a brand-new Android user, so every one of those settings is virgin — silently back to default — on every login. The user-visible need, from the script header: *"Chester's banking apps need compat mode, and GrapheneOS itself recommends it for them, so the setting has to survive the roam."*

**Why it has to be a framework patch.** Argued explicitly in the header. `GosPackageState` has **no shell read**: `edit-gos-package-state` (`PackageManagerShellCommand.java`) is the only entry point and every one of its verbs is a *write* — device-proven on lynx that `cmd package get-gos-package-state` returns `Unknown command`, rc=255. The only read is the binder API, and access to it is gated by a hardcoded appId table in `GosPackageStatePermissions` with no signature, device-owner or platform-cert door. Capture is therefore impossible without either a new read verb (architecture A′) or an entry in that table (A″, the maintainer's choice). This patch adds the entry.

**What it changes.** One additive block spliced immediately after the Settings grant: a seven-line Nowhere comment plus `builder().readWriteFlags(settingsReadWriteFlags).apply("com.nowhere.chooser", computer);`. It reuses GrapheneOS's own upstream **array** rather than a copied bit list, so the carry set tracks upstream automatically if GrapheneOS adds a hardening switch. Three omissions, each argued in the header and each load-bearing:

- **No `playIntegrityFlags`.** Bit 26 `PLAY_INTEGRITY_API_USED_AT_LEAST_ONCE` is derived usage bookkeeping, not a user setting — and it is the only `GosPackageState` found in the wild on the test device (toonblast, `flags-1=67108864`). Because `filterRead()` masks every read to the caller's granted flags, withholding it makes bit 26 **structurally unreadable** by the chooser rather than merely filtered in Nowhere's own code. The grant *is* the allowlist.
- **No storage-scopes / contact-scopes fields or their enable flags.** Both are blocked by design for roaming — the storage blob embeds the source user id as a literal path; the contact blob is raw contacts-DB row ids.
- **No `crossUserPermission` of any kind.** Capture and apply both run from *inside* the roamed user, so `targetUserId == callingUserId` and `checkCrossUserPermissions()` short-circuits. The `CROSS_USER_PROFILE` variants would not have helped regardless: they require `getProfileParentId(target) == caller`, and Nowhere's roamed users are independent secondaries, not work profiles. `ALLOW_CROSS_ANY_USER_WRITES` rides only on `createFull()` and is deliberately not requested.

The file is rewritten with `newline='\n'` (forced LF).

**Artifact and partition.** `frameworks/base/services/core` → **`services.jar`**, so the partition is **system**. AGENTS.md states it: *"Lands in `services.jar` → needs a full `m` and a `system` reflash."* Note **a full `m`**, not `m systemimage`. The script itself names no artifact; this comes from AGENTS.md and the `NWP-20260821-17` worklog entry.

**Idempotency.** Yes. The marker is the literal `com.nowhere.chooser` anywhere in the file; if present it prints `[gos-chooser-grant] chooser grant already present -- skipped` and exits 0 (after the mask assertion, which always runs). A missing anchor prints `[gos-chooser-grant] PATCH ANCHOR NOT FOUND (upstream changed?) -- aborting` and exits 2 — which, since `NWP-20260822-08` hardened `build-device.sh`, **fails the build** rather than shipping a silently unpatched image. `set -euo pipefail`; a missing target file prints `[gos-chooser-grant] MISSING <path>` and exits 1.

**If it is not applied.** The build does not break — it degrades, and the degradation is dangerous enough that the whole client design is built around it. Without the grant the chooser's `GosPackageState` reads and writes are all denied, and **a denied read returns `NONE` byte-identically to "this package has no state."** A naive capture would therefore read nothing for everything, write an empty file, and destroy every per-app hardening setting the user had — silently and permanently, on the first logoff. That is why the chooser enforces the safety invariant: a sealed row may only be *dropped* against a positive apply receipt. Receipt-gated, the actual worst case is that nothing roams and the sealed state is carried forward untouched — AGENTS.md: *"the safe direction, but it means nothing roams."*

**How to verify a build carries it.** On a build that carries it, logcat shows `gos apply user=<N>: <n> applied` at login (`core/chooser/src/com/nowhere/chooser/GosState.java`, the `Log.i` of `gos apply user=`, ~:146). Its absence shows as, at ERROR level (`GosState.java`, the `Log.e` of `gos apply: ALL`, ~:153-154):

```
gos apply: ALL <n> writes failed -- is gos-chooser-grant.sh applied to this image? Sealed state will be carried forward untouched.
```

Behavioural close criteria from backlog **B35**, on a USER build: `gos apply user=<N>: <n> applied, 0 failed`; a profile that set compat mode on an app logs in with the toggle still ON; an app the user *cleared* comes back OFF (proving the receipt lets a clear stick rather than carrying forward forever); and — the deliberately destructive case — on a build **without** the patch the sealed file is byte-identical after a logoff. Source-side: grep `GosPackageStatePermissions.java` in the tree for `com.nowhere.chooser`.

**Mask assertion (`NWP-20261014-38`).** Before the idempotency exit — so it runs on every build, including over an already-patched tree — the script finds exactly one `GosPackageStateFlag.java` under `frameworks/base`, reads `MASK` from the repo's `core/chooser/.../GosState.java` (resolved relative to the script), strips comments, and requires every set bit of `MASK` to be a live `NAME = <int>` index. Build-log tell: `[gos-chooser-grant] mask 0x1ffffc2 ⊆ live flag indices (<count> constants)`. Failure, exit 2 (fails the build): `[gos-chooser-grant] MASK BIT <n> (0x… in GosState.MASK) is NOT a live index in <file> -- …`, or `CANNOT DETERMINE …` when the enum file is absent or ambiguous or `MASK` cannot be read. Suite: `editions/endospore/build/test-gos-mask-guard.sh [--mutate]`, in CI.

The chooser is platform-signed and ships in the image, so it qualifies — but on a debuggable build a miss *throws* (`GosPackageStatePermission.java`: `if (Build.IS_DEBUGGABLE) throw new IllegalStateException(msg)`). ### `vpn-lockdown-on-first-connect.sh`

`editions/endospore/build/patches/vpn-lockdown-on-first-connect.sh` — **NWP-20260925-02**, implementing the DECIDED
entry of 2026-09-25 in `docs/product-decisions.md` (*“a VPN's "Block connections without VPN" arms on its FIRST
CONNECTION, not at the permission tap”*). The finding is `NWP-20260925-01`.

**What it patches.** Two files in `frameworks/base/services/core/java/com/android/server/`:
`VpnManagerService.java` — the GrapheneOS hunk in `setVpnPackageAuthorization` (commit `362020040a3c`, *“Set
always-on and lockdown on by default on first vpn connection at system_server side”*), the constructor, the binder
entry `setAlwaysOnVpnPackage`, one import, and two new private helpers placed after it — and `connectivity/Vpn.java`,
where a static hook field is added and called from `agentConnect`.

**Why it exists.** GrapheneOS arms always-on WITH lockdown the moment a VPN app's consent is approved. A VPN that
signs in through the browser asks for that consent before it can connect — Tailscale raises the dialog by itself
when opened signed out — so the user approves a kill switch no tunnel can satisfy yet. On frankel (user build
`2026092405`, 2026-09-25) the block stopped Tailscale's own sign-in page, cut every other app in the session off
the network (CoachUSA's WebView: `net::ERR_NAME_NOT_RESOLVED`), and nothing on screen said why. The device evidence
is in the backlog row *“Approving a VPN app’s permission switches on “Block connections without VPN” before the app
has signed in”*.

**Why it has to be a framework patch.** The arming happens inside `system_server`, in the same binder call that
records the consent; nothing outside it can stop it. A userspace alternative exists in principle — the agent could
undo the consent's lockdown with the #159 `np.VpnAlwaysOn` helper and re-arm it once `dumpsys connectivity` shows
the VPN connected — but it would poll every session as root, and every app would be blocked from the tap until the
undo landed. The decision named a framework patch.

**What it changes.**
1. **The consent.** For any VPN kind it sets always-on WITHOUT lockdown and records the package in the per-user
   Secure setting `nowhere_vpn_lockdown_pending`. The "is it already the always-on app?" check, the set and the write
   are one step under `mVpns`, so an explicit always-on call lands wholly before it (and the consent skips) or wholly
   after it (and wins). If the setting cannot be written it FAILS CLOSED — it arms the block at once, exactly as upstream does —
   rather than leave a VPN that can never be locked down. Then it posts one arm attempt (an app prepared earlier may
   already be connected).
2. **The connection.** `Vpn.agentConnect`, right after `updateState(CONNECTED)`, calls the static hook
   `Vpn.sNowhereOnConnected` with the user id; the `VpnManagerService` constructor points it at a post of the arm to
   `mHandler`. The field sits AFTER `mLockdown`, so upstream's javadoc and `@GuardedBy("this")` stay on that field.
   `agentConnect` is the one point every VPN kind passes through on connecting — a VpnService app via
   `establish()`, a platform (VpnManager IKEv2) profile via its runner, and the agent restart a lockdown change
   causes — so there is no carve-out. The hook only posts; it runs with the `Vpn` monitor held. Arming off the
   connecting thread matters because a lockdown change on a connected VPN restarts its network agent, exactly as
   toggling the block in Settings does.
3. **The arm.** Under `mVpns`, it reads the pending setting and sets lockdown only while always-on is still that
   package, the block is still off and the VPN is connected. A pending state that no longer applies is cleared; one
   that is merely early (not connected yet, or the user not running) is kept for the next connection. It is wrapped
   in a `RuntimeException` guard: it runs on `system_server`'s VpnManagerService handler thread, where an uncaught
   throw would take the whole process down. The restart it causes re-enters `agentConnect` and posts again; that
   second arm finds the pending state cleared and does nothing.
4. **An explicit choice wins.** `setAlwaysOnVpnPackage` — the entry Settings, a device policy and Nowhere's #159
   helper all use — clears the pending state once its own setting has SUCCEEDED, under `mVpns`, where the arm reads
   it too. A call that fails leaves the deferred block to arm.

Lock order is `mVpns` → the `Vpn` monitor on every new path, the same order upstream's `establishVpn` already takes.

The pending state is a Secure setting rather than memory so that it survives a user stop — a Nowhere cold-lock —
between the consent and the first connection; it dies with the user. Writing it never throws: a failure is logged,
so an always-on call for a user without settings still returns upstream's answer, and the consent fails closed.

**Artifact and partition.** `frameworks/base/services/core` → **`services.jar`** → **system**, via a full `m`
(`build-device.sh` builds `target-files-package`).

**Idempotency.** The marker `nowhere-vpn-first-connect (NWP-20260925-02)` is checked in BOTH files, and the cut is
named by a revision (`… rev 4`) stamped into BOTH — the `Vpn.java` hook comment and the `VpnManagerService`
constructor comment — and required in both, after `keystore-roam.sh`'s `PATCH_VERSION` lesson. Both files at the
current revision: `already applied (no change)`, exit 0. Both marked but either at an older cut: refused — `tree
carries an OLDER cut … revert with: <command>` — never reported applied while it ships older code. Only
`VpnManagerService.java` marked: refused as `an OLDER cut (rev 1 patched VpnManagerService.java only) or is
HALF-APPLIED`, because rev 1 is the likelier state. Only `Vpn.java` marked: refused as `HALF-APPLIED`. Every state was
exercised on the build host (pristine, re-run, rev 1, 2 and 3, both mixed pairs, and the real tree carrying rev 3). Either refusal fails the build (`NWP-20260822-08`), and both
print the revert, `git -C <tree>/frameworks/base checkout -- services/core/java/com/android/server/VpnManagerService.java
services/core/java/com/android/server/connectivity/Vpn.java`; no other patch touches either file. **Bump the revision
whenever the injected code changes.** Each of the six anchors must match exactly once, otherwise the script exits
non-zero naming it. Revisions 1 and 2 never shipped: both were replaced after adversarial review on the build host. Rev 3 is the cut
proven on lynx `2026092603`; rev 4 differs from it only in the stamp comment and the shell guard (a review of rev 3
found the stamp was in one file only), so its compiled code is identical.

**If it is not applied.** Nothing breaks: the consent arms the block at once, which is upstream GrapheneOS, and the
trap is back.

**Roamd drives this path too (`NWP-20261010-15`).** A block carried across a sign-out (the 2026-10-10 decision) is
re-applied by roamd's `vpnup` through the same consent — `np.VpnAlwaysOn <uid> <pkg> defer` calls
`setVpnPackageAuthorization` — so every sign-in with a carried ON depends on this patch exactly as a permission tap
does. Without it that sign-in arms the block at once: `roam.log` then reads `read back … lockdown=1 pending=null`
straight after `via defer`, where a patched image reads `lockdown=0 pending=<pkg>`.

✅ **DEVICE-PROVEN 2026-09-25 on lynx 2026092603** (Tailscale, VpnService path): the permission tap left the block off with the package pending, the first connection armed it, and a block turned off by hand stayed off across a reconnect — `docs/backlog.md` §H. Not yet exercised: a platform (IKEv2) profile, and a cold-lock between the tap and the first connection.

**How to verify a build carries it.**
- **Device:** approve a VPN app's permission in a session. logcat shows `VpnManagerService: Nowhere:
  always-on VPN set for user <N>; the block waits for its first connection`, and `settings get --user <N> secure
  always_on_vpn_lockdown` reads `0`. When the tunnel comes up: `Nowhere: VPN block armed at the first connection for
  user <N>`, and the setting reads `1`. Without the patch it reads `1` straight after the tap.
- **Artifact, no device:** the log text is a string literal, so it survives in the DEX pool of
  `SYSTEM/framework/services.jar` in the `target_files.zip`. Grep it for `Nowhere: VPN block armed at the first
  connection`, paired with a control that must match in the same file (`has no Vpn configuration`).

### `endospore-gmscompat-chooser-exempt.sh`

`editions/endospore/build/patches/endospore-gmscompat-chooser-exempt.sh` — the script header attributes it to **DIA-20260801, extended DIA-20260802-10**. It was originally applied by hand and lived only in the build tree (commit `266a4a0`: *"applied by hand and lived only in the build tree (a clean checkout would lose them)"*), formalized as a patch script by `DIA-20260802-08` (PR #531, merge `1ddd5fa`, branch `dia-20260802-08-framework-patch-scripts`), then extended with exemptions 2 and 3 by `DIA-20260802-10` (commit `5fcec67`, PR #533, merge `f36c6b0`). Docs: `docs/sandboxed-play-roam.md`, [`docs/ondemand-sandboxed-play-group.md`](ondemand-sandboxed-play-group.md).

**What it patches.** `frameworks/base/services/core/java/com/android/server/pm/PackageInstallerSession.java` — the GmsCompat install-protection guard condition, whose last term upstream is `&& !android.util.PackageUtils.getFirstPartyAppSourcePackageName(mContext).equals(initiatingPackageName)) {`. Referenced symbols: `initiatingPackageName`, `mInstallSource.mInstallerPackageName`, `isArchivedInstallation()`.

**Why it exists.** GrapheneOS's `PackageInstallerSession` blocks a non-first-party installer from installing the GmsCompat packages (`com.google.android.gms` / `com.android.vending`) — *"blocked to prevent breaking gmscompat"*. The amnesiac roam reinstalls the exact sealed, already-sanctioned APK version via `com.nowhere.chooser`, which is neither shell nor the first-party app source, so the reinstall was refused and sandboxed Play could never roam. User-visible symptom, from `docs/sandboxed-play-roam.md:10-15`: `PackageInstallerSession … destroyed because of [Installation of com.android.vending is blocked to prevent breaking gmscompat]` → `appcode install failed` → `NameNotFoundException` — *"the kept Play apps never come back, and the account goes with them."* The `DIA-20260802-10` half: the on-demand group-materialize tier raises Play Store as an **archived placeholder** at login, and the same block killed it (`Session destroyed ... blocked ... gmscompat`), so there was no Play Store icon to tap.

**What it changes.** It widens the guard with three additional negated terms, so the block no longer fires when any of them holds:

1. `&& !"com.nowhere.chooser".equals(initiatingPackageName)` — the normal `installApkSet` roam path (DIA-20260801 / #531).
2. `&& !"com.nowhere.chooser".equals(mInstallSource.mInstallerPackageName)` — the **on-demand** paths. `installPackageArchived` and the tap-time unarchive carry the *sealed package's original installer* as `initiatingPackageName`, not the chooser, so #531's initiator-only test missed them entirely. The chooser is always the real *installer of record*, so match on that too.
3. `&& !isArchivedInstallation()` — an archived placeholder installs no code (it is a code-less shell), so it cannot "break gmscompat"; the real code install (unarchive/tap) stays gated by (1)/(2).

The script handles two tree states. **Case A**, a tree already carrying the #531 initiator-only exemption, gets terms 2+3 appended (`added installer + archived exemptions to the #531-patched block`). **Case B**, a pristine upstream tree, gets all three at once (`applied chooser + installer + archived exemptions (pristine tree)`).

**Artifact and partition.** Not stated by the script. Derived from the path: `frameworks/base/services/core` → **`services.jar`** (system_server), partition **system**. Same class as `gos-chooser-grant.sh`, so a full `m` plus a system reflash.

**Idempotency.** Yes. The marker is the exemption-2 string `com.nowhere.chooser".equals(mInstallSource.mInstallerPackageName)`, chosen (per the script's own comment) because it *"uniquely identifies the full patch"* — which is what makes it correctly re-patch a tree carrying only #531's older half rather than declaring victory on it. Already applied → `[gmscompat-exempt] full exemption (initiator+installer+archived) already applied -- skipped`, exit 0. Neither anchor found → `[gmscompat-exempt] PATCH ANCHOR NOT FOUND (upstream changed?) -- aborting`, exit 2, which fails the build under `build-device.sh`. Missing target file → exit 1.

**If it is not applied.** The build does not break; the feature dies at runtime. Script header, verbatim: *"Without this patch on the image, sandboxed Play does not roam (pre-DIA behaviour); without exemptions 2/3, an ON-DEMAND (group-materialize) Play Store can't raise its placeholder so there is nothing to tap."* The install is refused with the gmscompat message and the Google account goes with the apps.

**How to verify a build carries it.** No positive log line is given — verification is by absence plus behaviour. Absent: `PackageInstallerSession … destroyed because of [Installation of com.android.vending is blocked to prevent breaking gmscompat]` should not appear at roam-in or at on-demand materialize. Present: the kept Play packages reinstall on a roam, and on the on-demand tier the archived Play Store placeholder appears and can be tapped. Source-side, on the build tree: grep `PackageInstallerSession.java` for `com.nowhere.chooser".equals(mInstallSource.mInstallerPackageName)`.

### `endospore-gmscompat-incremental-hide.sh`

`editions/endospore/build/patches/endospore-gmscompat-incremental-hide.sh` — the script header says **"(DIA-20260802)"**; the commit is `DIA-20260802-08`, `703f17c`, merged in PR #531 (merge `1ddd5fa`, branch `dia-20260802-08-framework-patch-scripts`, 2026-08-02). **What it patches.** `frameworks/base/core/java/com/android/internal/gmscompat/sysservice/GmcPackageManager.java`, anchored on the entire existing `@Override public boolean hasSystemFeature(String name)` override — the one that already spoofs `android.hardware.uwb` as absent. Two **new** overrides are appended after it: `hasSystemFeature(String name, int version)` and `getSystemAvailableFeatures()`, both gated on `GmsCompat.isPlayStore()` / `GmsCompat.isGmsCore()`.

**Why it exists.** Sandboxed Play (GrapheneOS gmscompat) runs `com.android.vending` / `com.google.android.gms` **unprivileged**, so they cannot hold the signature permission `USE_INSTALLER_V2` and cannot perform incremental/streaming (DataLoader) installs. Finsky nevertheless *attempts* a streaming install for large (streaming-flagged / App-Bundle) apps and hard-fails on the first try — `Session creation failed errorCode=5402` / `SecurityException: You need the com.android.permission.USE_INSTALLER_V2 permission to use a data loader`. On the amnesiac roam this recurs on the *first* big-game install after **every** login (Play is cold and un-synced), *"which reads as broken even though it self-heals."*

**What it changes.** It makes the sandboxed-Play `PackageManager` wrapper report `FEATURE_INCREMENTAL_DELIVERY` as absent, so Finsky never attempts streaming and full-installs on the first tap. Two overrides appended after the uwb-spoofing one:

1. `hasSystemFeature(String name, int version)` returns `false` when `(GmsCompat.isPlayStore() || GmsCompat.isGmsCore()) && PackageManager.FEATURE_INCREMENTAL_DELIVERY.equals(name)`, else delegates to `super`. Per the in-patch comment the 1-arg form *"delegates virtually to this 2-arg form"*, so both are covered.
2. `getSystemAvailableFeatures()` returns `super`'s array untouched when it is null or the caller is not Play/GMS; otherwise it copies into an `ArrayList`, skipping the `FeatureInfo` whose name is `FEATURE_INCREMENTAL_DELIVERY`.

Both paths are covered "so it works whether Finsky queries or enumerates". It is per-app by construction: `GmcPackageManager` exists only in gmscompat processes, and the `isPlayStore()`/`isGmsCore()` gate narrows it further — adb, `pm install`, system and every non-gmscompat app keep incremental delivery.

**Artifact and partition.** Not stated by the script. Derived from the path: `frameworks/base/core/java` is the boot-classpath **framework** module → **`framework.jar` in `/system/framework`** (and the boot image built from it), *not* `services.jar` and *not* an APK. Partition: **system**.

Anchor block not found → `[incremental-hide] PATCH ANCHOR NOT FOUND (upstream changed?) -- aborting`, exit 2 (fails the build under `build-device.sh`). Missing target file → exit 1. Separately it is **fail-open at runtime** by the header's own description: if the wrapper is inactive the real feature is reported and nothing crashes.

**If it is not applied.** The build does not break, and the feature self-heals — the mildest of the four. Header, verbatim: *"Without this patch the first post-roam big-game install shows a 5402 error and needs a manual retry."* The retry falls back to a full-APK install and succeeds. So the cost is a user-visible "Can't install \<app\> - Try again" on the first big install after every login.

**How to verify a build carries it.** No positive log line is given; verification is behavioural or by absence. ### `libselinux-pkgdir-uid-aliasing.sh`

`editions/endospore/build/patches/libselinux-pkgdir-uid-aliasing.sh` — **DIA-20260806-15** (commit `9bd24b6`, PR #574, merge `d43d74d`, branch `dia-20260806-15-libselinux-uid-aliasing`) is the root-cause fix; **DIA-20260806-16** (commit `9632d4c`, PR #575, merge `7c40079`) then fixed the patch script's own anchor bug. Backlog row "libselinux relabel no longer corrupts roamed app labels", NEEDS-DEVICE, closing evidence *"a roam with a broad app set"*. It corrects the record of `DIA-20260806-10` and `-11`, and cites #570.

**Scope, stated honestly.** It is filed under Endospore, but **the bug is not GrapheneOS-specific at all** — neither a strictness workaround nor a feature integration. The header says so: *"upstream libselinux, reachable on any Android device via `restorecon -D`."* It lives in `editions/endospore/build/patches/` because that is where it was found and applied, and it reaches a tree **only** via the endospore glob at `build-device.sh` (`for p in $PATCH_LIST` loop, ~:223). Nothing in the Diaspore build path applies it — the Diaspore build applies no patches automatically at all — and it is not in AGENTS.md's mandated list either. Worth flagging against AGENTS.md's lowest-tier rule; this extraction made no edit.

**What it patches.** `external/selinux/libselinux/src/android/android_device.c`, the function `pkgdir_selabel_lookup()`. Also named in the header, though not edited: `package_info_lookup()` (whose borrowed pointer *is* the bug), `package_info_init()` (the wrong function the first version of this script edited), `seapp_context_lookup()` (which turns the corrupted uid into MCS categories), `selinux_android_restorecon_pkgdir()` and `restorecon_sb()`.

**Why it exists.** An upstream aliasing bug. `pkgdir_selabel_lookup()` does `info->uid += userid_from_path * AID_USER_OFFSET;` on a pointer **into the process-global `pkgTab` hash** — a cache parsed once per process from `/data/system/packages.list`. The `+=` was meant as a local adjustment but writes back into the shared entry, so the Nth lookup of a given package within one restorecon process yields `uid = appid + N * userid * AID_USER_OFFSET`, i.e. a derived userid of N times the real one. `seapp_context_lookup()` turns that into MCS categories, so a single `restorecon -R -D /data/user/10/<pkg>` walks c522 → c532 → c542 → … **+10 per entry in fts order.**

Measured on lynx 2026-08-06: **743/798 CE entries and 446/500 DE entries mislabelled, across 202 of 202 category-bearing packages.** From the header: *"Launcher3, contacts, MTP and cellbroadcast all crashed with SQLiteCantOpen / 'Permission denied' on their own databases, because the app's process context (c522) no longer dominated its own files (c532, c542, c662, ...)."* The precise user-visible line — **Launcher3 crashloops on a roamed user**, `SQLiteCantOpen ... /data/user/10/com.android.launcher3/databases/launcher.db ... Permission denied` — plus the totals "~1,189 mislabelled entries" and "51 crashes" come from the `DIA-20260806-15` worklog row, not from the script header.

**Why it hid**, three reasons, all of which were hit at once:
- `installd` never executes the branch — it calls `selinux_android_restorecon_pkgdir()` *with* seinfo and the mutation sits inside `if (!seinfo)`. Only the `/system/bin/restorecon` CLI reaches it.
- User 0 is immune: `userid_from_path` is 0, so the added term is 0. Any comparison against an unroamed device therefore looks clean.
- `restorecon` is **self-consistent**: a fresh process rebuilds the cache and re-derives the *same* corrupted sequence, so `restorecon -n` reports nothing to change. *"The corruption is a fixed point of its own walk."*

**Why it has to be a patch.** It is a C library bug in libselinux reached only from the `/system/bin/restorecon` CLI path; there is no app-level or script-level door to it. The repo's script-level mitigation was separate and different in kind — `DIA-20260806-15` also *removed* `-D` from the five app-data walks in roamd and the agent, making the buggy branch unreachable in normal operation. This patch is the real fix underneath that.

**What it changes.** Three mechanical edits, all inside `pkgdir_selabel_lookup()`, computing into a local instead of mutating the cached entry — header: *"One statement, no behaviour change for any correct caller."*

1. Declares `uid_t nowhere_resolved_uid = uid;` (with a three-line explanatory comment) immediately after the **first** `struct pkg_info *info = NULL;` that follows the `static int pkgdir_selabel_lookup(` signature.
2. Replaces `info->uid += userid_from_path * AID_USER_OFFSET;` with `nowhere_resolved_uid = info->uid + userid_from_path * AID_USER_OFFSET;`.
3. Replaces every occurrence of the read expression `info ? info->uid : uid` with `nowhere_resolved_uid`, printing the count of redirected read sites.

Written back with `newline=''` (no translation). The header notes the fix is *"Worth reporting upstream."*

**Artifact and partition.** Not stated by the script. Derived from the path plus `DIA-20260806-16`'s commit message (*"Verified with `m libselinux` (157 steps, build succeeded) before pushing"*): the **libselinux library** (`libselinux.so` on `/system`, plus its static consumers), reached at runtime by the `/system/bin/restorecon` CLI. Partition: **system**. It is not `services.jar`, not `framework.jar` and not an APK, so it does not need the full-`m`-plus-`services.jar` treatment the framework patches do — but the system image must be rebuilt and reflashed.

**Idempotency.** Yes. The marker is the literal `nowhere_resolved_uid` → `[libselinux-uid] already applied`, exit 0. Note the **different exit code from its siblings**: every failure path here exits **1**, not 2 (still non-zero, so `build-device.sh` still fails the build). Five separate assertions, the first four added or hardened by `DIA-20260806-16`: the mutating statement `\t\tinfo->uid += userid_from_path * AID_USER_OFFSET;` must be present; `static int pkgdir_selabel_lookup(` must be found; a `struct pkg_info *info = NULL;` declaration must exist **after** that signature; and the declaration site must **precede** the mutation site — *"or we are editing the wrong function."* The fifth, `NWP-20261026-16`: at least one `info ? info->uid : uid` read site must be found, checked before the only write, else exit 1 with the file untouched — removing the `+=` with no reader redirected would drop the user offset from every lookup and still report success. `editions/endospore/build/test-libselinux-uid-patch.sh` runs the apply, the re-run and the five refusals against a synthetic tree in CI.

**If it is not applied.** The build does not break, but the failure is the worst of the four in kind — silent **data-label corruption**, not a missing feature. **Why it exists.** #176 SIM-picker parity. ### `system-userdir-guard.sh`

`editions/diaspore/build/patches/system-userdir-guard.sh` — suite `editions/diaspore/build/test-system-userdir-guard.sh`, run by CI with its `--mutate` pass in the step *“A removed user's /data/system/users/<n> stays gone (NWP-20261003-01)”*, which also runs the roamd half's suite, `core/vendor-common/bin/test-userdir-orphan.sh`. Both the patch and its suite need python3.

**What it patches.** Five files in `frameworks/base`, at seven whole-line anchors, each matching exactly once in the GrapheneOS tree (`grapheneos-2026061600`, frameworks/base `1fe8459c`) and in the LineageOS tree (lineage-22.2, frameworks/base `673bad10`). All five files are pristine in both trees, and no other Nowhere patch touches them.
- `core/java/android/util/AtomicFile.java` — `startWrite`, inside its `catch (FileNotFoundException e)`, after `File parent = mNewName.getParentFile();` (GrapheneOS `:150`, LineageOS `:152`).
- `services/core/java/com/android/server/pm/ResilientAtomicFile.java` — `startWrite`, before the unconditional `new File(mFile.getParent()).mkdirs();` (`:89`, `:88`).
- `services/core/java/com/android/server/biometrics/sensors/BiometricUserState.java` — `doWriteStateInternal`'s `catch (Throwable t)`, before `Slog.e(TAG, "Failed to write settings, restoring backup", t);` (`:106` in both).
- `services/core/java/com/android/server/pm/UserDataPreparer.java` — `prepareUserDataLI`, after the new-user recovery's `destroyUserDataLI(volumeUuid, userId, flags);` (`:138`, `:135`).
- `services/core/java/com/android/server/pm/UserManagerService.java` — three blocks: in the constructor after `readUserListLP();` (`:1237`, `:1089`); in `createUserInternalUncheckedNoTracing` before `Environment.getUserSystemDirectory(userId).mkdirs();` (`:6525`, `:5788`); and a new private static helper before `packageToRestrictionsFileName` (`:8090`, `:7287`).

**Why it exists.** `docs/backlog.md`, *“A reaped user's `/data/system/users/<id>` is re-created by a framework writer AFTER the reap removed it, and survives as a cleartext orphan that the next user given that id adopts”*. On lynx `2026100113`, 2026-10-02, odtest57's `users/11` held `settings_secure.xml` and `settings_ssaid.xml` written after the reap had removed the directory, with no `11.xml`. On lynx on 2026-10-03 (`2026100112`'s system and system_ext, flashed that day over `2026100113`), AppIdleHistory re-created `users/11/app_idle_stats.xml` for a user 11 that no longer existed (`am set-standby-bucket --user 11 …`, then `dumpsys usagestats flush`). The directory is under the system's own DE key, so it is cleartext, and it is outside every user, so the boot-wipe never reaches it. `settings_ssaid.xml` holds the profile's SSAID userkey and its per-app ANDROID_IDs. The orphan survives reboots, ids restart at 10, and, from GrapheneOS source (no id has yet been seen loading one on a device; the creation-discard step's control, below, is the check that would show it), the next user given that id loads it as its own state inside `createAndManageUser`, before any Nowhere code runs.

**Why it has to be a framework patch.** The writers are inside system_server, and they write for a removed user at times nothing outside it can bound: SettingsState's whole-map write after any change to a state rebuilt for that user, and AppIdleHistory's flush (UsageStatsService's, 20 min after the first usage event since the previous one, so it follows activity) and shutdown flush. Every one of them reaches the disk through one call, the parent `mkdirs` in `AtomicFile.startWrite` — or, for package-restrictions, the unconditional `mkdirs` in `ResilientAtomicFile.startWrite`. roamd's reap can re-check only inside its own window. roamd's boot sweep runs asynchronously after boot, and nothing orders it before the first `createAndManageUser`, which is where, from source, the adoption happens. So only a refusal inside those two classes stops every such write at its source, and only a discard inside UserManagerService's own id allocation is ordered before the load by construction. The backlog row's first root-cause direction, a SettingsProvider patch that refuses to rebuild a dropped user's state, was set aside in this slice: it stops one writer, while AppIdleHistory is a second, independent one and package-restrictions and RegisteredServicesCache write the same way.

**What it changes, mechanically.** One invariant: UserManagerService and its UserDataPreparer create `/data/system/users/<n>` (empty, for a new user), and `AtomicFile` and `ResilientAtomicFile` never re-create a missing one.
- **`AtomicFile`** (framework.jar), only on the path where opening `<file>.new` has already failed. It walks up from the parent. At the component directly under `/data/system/users`, if the name is numeric, not `0`, and `!isDirectory()`, it logs `AtomicFile: nowhere: refused to re-create the missing system dir of user <N> for <writer> via <Debug.getCallers(5)> (NWP-20261003-01)` and throws `IOException("nowhere: missing user system dir not re-created (NWP-20261003-01)")`. The refusal has the stock shape, an `IOException`, as a failed `mkdirs` already throws, so every caller's existing catch handles it. Anything else is stock: a missing subdirectory of an existing `users/<n>` (`registered_services/`, for one) is still created. `<writer>` is the file's basename only when it is one of eight fixed names (`settings_secure.xml`, `settings_system.xml`, `settings_ssaid.xml`, `settings_config.xml`, `app_idle_stats.xml`, `package-restrictions.xml`, `appwidgets.xml`, `wallpaper_info.xml`) or fully matches `settings_(fingerprint|face)(_[0-9]+)?[.]xml`, whose only variable part is a sensor id. Anything else is logged as `other`, because an application-restrictions file is named `res_<package>.xml`. The exception message carries no path and stays clear of SettingsState's `Couldn't create directory` retry text.
- **`ResilientAtomicFile`** (services.jar): the same guard before its unconditional `mkdirs`, so a package-restrictions write is refused the same way. PackageManager then logs its stock `Slog.wtf` *“Unable to write package manager package restrictions…”*, which is not fatal in system_server.
- **`BiometricUserState`** (services.jar). Stock rethrows a failed state write as an `IllegalStateException` on an AsyncTask worker, which is an uncaught exception in system_server and restarts the runtime. The block drops exactly the refusal (an `IOException` carrying the literal above) and logs `UserState: nowhere: dropped a biometric state write for the missing system dir /data/system/users/<N> (NWP-20261003-01)`. Any other failure still takes the stock path.
- **`UserDataPreparer`** (services.jar). When preparing a NEW user's storage fails, stock deletes that live user's `users/<n>`, retries, and lets the user carry on, relying on the next writer's `mkdirs` to bring the directory back. Under the guard every one of that user's writes would be refused, so the block re-creates the directory, empty, under the same condition the delete used, and logs `UserDataPreparer: nowhere: re-created the system dir of new user <N> after a failed prepare (NWP-20261003-01)`, or, at E, `nowhere: could not re-create the system dir of new user <N> after a failed prepare (NWP-20261003-01)` when it cannot.
- **`UserManagerService`, at user creation**, straight after the id is allocated and before the user record, `prepareUserData` or anything else that could load from the directory. It discards whatever `users/<n>` holds and logs `UserManagerService: nowhere: user <N> starts with an empty system dir, <k> stale entries discarded (NWP-20261003-01)`. If anything is left, it keeps the id out of use for the rest of the boot (`mRemovingUserIds`, under `mUsersLock`) and fails that creation with `nowhere: the stale system dir of user <N> could not be discarded, <j> entries left (NWP-20261003-01)`. The chooser's `createRoamUser` then returns -1, that sign-in fails once as ERR-CREATEUSER, and the next creation is given another id.
- **`UserManagerService`, at every boot**, in the constructor after the user list is read and before the service is published — so before any sign-in, app, BootReceiver or roamd sweep of that boot. Every numeric `users/<n>` other than `0` whose user it did not read is discarded (partial users have been read by then, so they are kept). One line per boot: `UserManagerService: nowhere: discarded <k> orphan system dir(s) of removed users at boot (NWP-20261003-01): user ids [<ids>]`, `[]` when k is 0. A directory it cannot discard keeps its id out of use for that boot and is reported at W: `nowhere: <j> entries of orphan system dirs could not be discarded at boot; their ids stay unused until the next boot (NWP-20261003-01): user ids [<ids>]`. Both id lists can hold nothing but integers.
- **The delete helper**, `nowhereGuardDelete`, a private static member of UserManagerService that both discards use. It logs nothing (stock `FileUtils.deleteContents` logs every path it fails to delete, and a `res_<package>.xml` would put a package in logcat), never follows a symbolic link, lets no filesystem error escape (the boot discard runs in the constructor, where a throw would bootloop the phone for as long as the orphan exists) — `File.toPath()` included, which throws `InvalidPathException` for a name the UTF-8 encoder rejects, so it sits in a try of its own and counts such an entry as left — and returns the number of entries it could not remove.

Every log line carries counts, user ids, the allowlisted names and, on a refusal, the five framework frames that called the write (`Debug.getCallers(5)`); none carries a package-named file or a profile name. The patch adds 197 lines in 7 hunks, identical in both trees, and removes none.

**Artifact and partition.** `AtomicFile` lives in `core/java` (`framework-core-sources` → `framework-minus-apex`, stem `framework`), so it lands in `framework.jar`. The other four live in `services/core/java` (`services.core-sources` → `services.core` → `services`), so they land in `services.jar`. Both module chains were read in the GrapheneOS tree's `Android.bp` files on the build VM on 2026-10-03, and the LineageOS tree defines the same modules. Both jars install to `/system/framework` → flash `system`. framework.jar is part of the boot image, so this needs a full `m`, not a single-module build.

**Idempotency.** Exit 0: applied, or already applied (`already applied (rev 1) -- skipped`, every file exactly at rev 1). Exit 1: a usage error, a missing file, or a failed self-check. Exit 2: anchor drift — any anchor in any file not matching exactly once — and nothing is written. Exit 3: an older or partial copy (any trace of the patch, in any file, that is not exactly rev 1); it names the files and prints `revert, then re-run: git -C <tree>/frameworks/base checkout -- <the five files>`, which is safe because no other Nowhere patch touches them. Each file is written to `<file>.nowhere-tmp`, re-read and self-checked; any failure removes every temp file and replaces nothing. The file mode is kept, and the marker `nowhere-userdir-guard rev 1` appears once per file. Applied on 2026-10-03 to scratch copies of both trees' five files, with the trees themselves untouched: exit 0, and a re-run skipped.

**If it is NOT applied.** Silent: no build break, no log line. A late framework write re-creates a removed user's `users/<n>`, and after a reboot the next user given that id loads it (from source, not yet seen on a device) — the previous profile's ANDROID_IDs, SSAID userkey and secure settings — unless roamd's boot sweep happened to empty it first. roamd's half still runs (the reap re-check, the boot sweep's `userdirs=`, the seed removals). It narrows the window, but it is not an adoption fence.

**Warnings.**
- ⚠ **It must ship in the same image as the roamd half of the slice** (`core/vendor-common/bin/nowhere_roamd.sh`). Before that change, roamd's reap began with an unconditional `rm -rf /data/system/users/<uid>`, and the #73 orphan sweep reaches that op for a uid whose `removeUser` may have failed — a possibly LIVE user, whose every write this patch would then refuse for the rest of its session. The roamd half removes that `rm`. Both arrive through the normal build: roamd is staged by `stage-vendor.sh`, and the patch is applied by `build-device.sh`, which fails the build if it does not apply. A Diaspore image carries roamd's half alone unless someone applies the patch by hand, which is the safe direction. ⚠ **But the GrapheneOS tree is shared, and `build-device.sh` never reverts a patch.** Once any build has applied this one, every later build from that tree carries it — including a build of a commit whose `GOS_MANDATED_PATCHES` does not name it, which never runs the patch and so logs nothing about it. Before building a commit that lacks the roamd half (main before this slice merges, or an older release branch), revert the five files: `git -C <tree>/frameworks/base checkout -- core/java/android/util/AtomicFile.java services/core/java/com/android/server/pm/ResilientAtomicFile.java services/core/java/com/android/server/biometrics/sensors/BiometricUserState.java services/core/java/com/android/server/pm/UserDataPreparer.java services/core/java/com/android/server/pm/UserManagerService.java` — the revert the script itself prints, safe because no other Nowhere patch touches those files. The same applies to a LineageOS tree patched by hand.

### recovery-rebrand.sh

### sepolicy-app-media-manage.sh

**What it patches.** Three areas of the AOSP/LineageOS/GrapheneOS sepolicy tree, never nowhere-phone source: `system/sepolicy/public/file.te` (a type declaration inserted after the `type media_rw_data_file, file_type, data_file_type, core_data_file_type, mlstrustedobject;` line, used as a unique anchor); `system/sepolicy/private/app_neverallows.te` (the app create/unlink neverallow's exemption list, anchored on `-app_data_file .*# The apps sandbox itself`); and, on frozen-API trees only, `system/sepolicy/prebuilts/api/<latest YYYYMM>/public/file.te` plus every `system/sepolicy/private/compat/<YYYYMM>/<YYYYMM>.ignore.cil` `  ( new_objects` list. Path in-repo: `editions/diaspore/build/patches/sepolicy-app-media-manage.sh`.

**Why it exists.** #84 on-demand media *deletion* (and later write-back). `nowhere_mediad` serves large deferred media through a per-app FUSE overlay whose files carried the type `nowhere_media_file`. A roamed app must be able to `unlink(2)` its own served file — the header's concrete case is Organic Maps updating a map by unlinking the old `<region>.mwm` before writing the new one. Under enforcing SELinux that needs `unlink` on `nowhere_media_file`, which AOSP's platform app create/unlink neverallow forbids for every file type outside the app-sandbox set. The exemption has to *name* the type inside that platform neverallow, and that neverallow is verified against a platform-only policy (the `sepolicy_neverallows` target: plat public + private, no system_ext/vendor) — so declaring the type in our SYSTEM_EXT_PRIVATE vendor dir fails there with `unknown type nowhere_media_file`. Hence the promotion of the declaration platform-side, with the exemption alongside it. Step 3 exists because a GrapheneOS release build additionally runs `se_freeze_test` and `treble_sepolicy_tests`, which reject a new public type unless it is present in the latest frozen public snapshot *and* ignored in every prior frozen version's `new_objects` list. **User-visible symptom:** the script header states none; the failure it describes is an app's delete/update of its own downloaded media returning EPERM (the Organic Maps map-update case). The Endospore half is a build failure, not a device symptom.

**What it changes, mechanically.** Three guarded textual edits. (1) If `nowhere_media_file` is absent from `public/file.te`: `cp` to `file.te.diaspore-orig`, then sed-insert a five-line comment block plus `type nowhere_media_file, file_type, mlstrustedobject;` after the `media_rw_data_file` declaration — `mlstrustedobject` is what bridges MLS so an app at `s0:cN` can touch this `s0` file (the header names `ringtone_file`/`ota_package_file` as the same trick). (2) If absent from `private/app_neverallows.te`: back up, sed-insert `  -nowhere_media_file       # #84: an app manages its OWN on-demand media (mediad FUSE, per-app dir)` after the `-app_data_file` line, with the same re-grep / restore / exit 1 guard. **Idempotence.** Yes, fully — each step greps for `nowhere_media_file` first and skips with a message (`already has the type (skip)` / `already exempt (skip)` / silent continue). ### nfc-deviceowner-readermode.sh

**What it patches.** `packages/apps/Nfc/src/com/android/nfc/NfcService.java`, the LineageOS NFC APEX source. Three symbols: `setReaderMode` — its `privilegedCaller |= packageName.equals(SYSTEM_UI);` line, anchored jointly with the following `Log.d(TAG, "setReaderMode: uid=" + callingUid` because the privilegedCaller line appears more than once; a new private helper `isDeviceOwnerUid(int uid)` inserted immediately before `computeDiscoveryParameters`; and `computeDiscoveryParameters` itself, where a new branch is inserted before the existing `} else if (screenState == SCREEN_STATE_ON_LOCKED && mInProvisionMode) {` provisioning branch. Path in-repo: `editions/diaspore/build/patches/nfc-deviceowner-readermode.sh`.

**Why it exists.** DIA-20260708 / #114, "NFC-for-resume". At a cold-lock resume a 2FA (needKey) session demanded the USB-C host-flip to hunt for a key; the flip (`ssusb/mode=host`, ~30s) degrades the FP3 NFC RF field, so a security-key tap during it loses the tag, making NFC resume effectively impossible even though the gate accepts an NFC tap at boot login. **User-visible symptom,** as stated by the origin commit: the tap "lost the tag (\"out of date\")" and NFC resume was effectively impossible. In-repo the framework rejection surfaces as logcat `setReaderMode: Caller is not in foreground` (quoted at `core/chooser/src/com/nowhere/chooser/ChooserActivity.java`, the "#114 (deferred)" comment, ~:1129).

**Why it has to be a framework patch.** The script states it directly: NfcService grants reader mode only to the ActivityManager-foreground app or SystemUI, and only recomputes discovery for a reader while the screen is unlocked. The cold-resume gate is neither — it draws **over** the keyguard as the locked auth screen, and the screen state is `SCREEN_STATE_ON_LOCKED` — and "There is no config toggle for 'let the device owner read NFC at the lock screen'". App-level work cannot reach it, and the failed attempt is documented: the chooser's own try, re-arming NFC from the keyguard-dismiss callback, is annotated in `ChooserActivity.java` ("#114 (deferred): re-arming NFC here does NOT help", ~:1126-1130) as ineffective because the cold-resume keyguard **flaps** (dismiss + relock) and NfcService grants reader mode only once it fully exits and the chooser is the true AM-foreground, tens of seconds later.

**What it changes, mechanically.** A guarded, Python-driven, three-part source edit with hard anchor-count asserts (each `assert s.count(anchor) == 1`, so upstream drift aborts before anything is written). (1) In `setReaderMode`, adds `privilegedCaller |= isDeviceOwnerUid(callingUid);` after the SYSTEM_UI privileged-caller line, with a #114 comment — treating the device owner as a privileged reader caller like SystemUI. (2) Inserts a best-effort helper `private boolean isDeviceOwnerUid(int uid)` that resolves `DevicePolicyManager`, maps the uid to packages via `PackageManager.getPackagesForUid`, and returns true if any is `dpm.isDeviceOwnerApp`; any `Throwable` is caught, logged `Log.w(TAG, "isDeviceOwnerUid", t)`, and returns false. (3) Inserts a new ON_LOCKED discovery branch ahead of the provisioning branch, taken when `screenState == SCREEN_STATE_ON_LOCKED && mReaderModeParams != null && isReaderOptionEnabled() && isDeviceOwnerUid(mReaderModeParams.uid)`; it maps `mReaderModeParams.flags` (`FLAG_READER_NFC_A/B/F/V/BARCODE`) to `NFC_POLL_A/B/F/V/KOVIO`, calls `paramsBuilder.setTechMask` and `setEnableReaderMode(true)`, and `setEnableHostRouting(true)` when flags are set but techMask is 0 — mirroring the existing unlocked reader branch. Both new gates are scoped to `isDeviceOwnerUid`, so no read-NFC-while-locked surface opens to ordinary apps. Runs under `set -euo pipefail`; backs up to `<file>.diaspore-orig` with `cp -n`.

**Artifact and partition.** The NFC service — **not** services.jar and **not** SystemUI. The script header (`nfc-deviceowner-readermode.sh`, "the com.android.nfcservices APEX", ~:16-18) and the origin commit both state it rebuilds the `com.android.nfcservices` APEX from `packages/apps/Nfc`. ⚠ The **partition is inference, not stated anywhere in-repo**: an updatable AOSP APEX of that name normally ships at `/system/apex/com.android.nfcservices.apex`, which would make **system** the partition to reflash. Confirm the built artifact's path under `out/target/product/<dev>/` before planning the flash rather than trusting this line. Run once on the build tree before `m`.

**Idempotence.** Yes. The first action after locating the file is `grep -q "isDeviceOwnerUid" "$NF"` → prints `already applied (no change)` and exits 0. The backup uses `cp -n`, so an existing `.diaspore-orig` is never clobbered by a re-run. The Python stage builds the whole modified string in memory and only calls `open(f, "w")` at the very end, so if any of the three anchor asserts fails the file is left **pristine** and, under `set -euo pipefail`, the script exits non-zero naming which anchor drifted (e.g. `anchor1 count %d -- setReaderMode privilegedCaller shape changed`). **If it is not applied.** The build does not break — it degrades quietly, and the repo's current code is written as if it *is* absent.
